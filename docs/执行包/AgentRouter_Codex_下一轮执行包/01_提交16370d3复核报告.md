Codex 的汇报基本诚实，且与仓库证据一致：

- pi 0.85.1 已探测并记录在 Windows 用户级 npm 目录；
- 13 组离线检查均为 PASS；

## 二、已经做得较好的部分

### 1. 没有把模拟测试冒充真实支持

仓库 README、阶段报告、兼容性锁都明确使用 `PROBED`、`BLOCKED_ENV`、`certified: false` 等状态。这一点正确，应继续保持。

### 2. 核心领域模型已经建立

已经存在项目、协作空间、角色、绑定、任务、Run、消息、结果、Outbox、等待、产物、审批、问题、账号、额度快照和切号操作等表。角色 ID、绑定 epoch、原生会话、业务任务和实际 Run 被区分开，方向正确。

### 3. 关键可靠性语义已有代码和测试

已经覆盖：

- 持久化成功后静默返回；
- 同一 `operation_id` 幂等；
- 相同 ID 不同载荷冲突；
- 结果只按显式目标投递；
- Handoff 在原生 Run 真正收尾前保持 HELD；
- 当前任务的关联结果优先续办；
- 独立任务 FIFO；
- 通知不自动唤醒；
- 原生结束但没有 `route_finish` 时进入注意状态；
- 未知 Run 在重启后不盲目重跑；
- 旧 binding epoch 不能释放当前资源；
- 同一物理工作区写入互斥；
- 频率限制与时钟回拨的保守处理。

这些是 AgentRouter 最难返工的语义基础，值得保留。

### 4. 本地桌面安全默认值较好

Electron Renderer 已启用 `contextIsolation`、禁用 Node 集成、启用 sandbox，并禁止任意导航和新窗口。目录选择也通过主进程授权，不允许 Renderer 随意传一个本地目录。

### 5. SQLite 设置偏向可靠性

启用了外键、WAL、`synchronous=FULL`、忙等待和完整性检查，符合本地单写者应用的方向。

## 四、必须修复或补齐的问题

### P0：下一轮必须先处理

#### AR-R01：Core daemon 还不是实际运行内核

`apps/core-daemon/main.ts` 只暴露 snapshot、项目和角色的少量管理方法。Core 中已有的 `send`、`finish`、`wait`、dispatch、settle、审批、产物、内部桥和适配器均没有接入 daemon。桌面看起来“连接 Core”，但实际上还不能驱动多 Harness 协作。

**要求：**建立正式的 Core Service API，所有桌面和未来外部客户端都调用它。

#### AR-R02：三家 Adapter 不是 Adapter

三个目录目前都只有终态事件转换文件，没有进程生命周期、握手、会话、Prompt、事件订阅、取消、审批、恢复和工具注入。

**要求：**先完成 Mock Harness 的完整 Adapter，再按 Codex、Kimi、pi 顺序做真实实现。

#### AR-R03：GUI 与本地 Core 强耦合

Electron 主进程固定启动 Windows 打包目录中的 `node.exe + core.mjs`，通过 stdio 连接；没有 `CoreTransport`，没有握手、事件游标、重连或远程连接。彻底退出桌面就会结束 Core。

**要求：**抽象 Local/Stdio/SSH 传输，并将 Linux Core 改为独立常驻进程。

#### AR-R04：真实联调日志存在泄密风险

`.gitignore` 先忽略 `*.log`，随后又显式允许 `evidence/**/*.log`。当前没有真实账号，因此尚未泄漏；一旦真实联调，Harness stdout/stderr、请求错误、账号标识或令牌片段可能被提交到私人仓库。

**要求：**仓库只允许提交经过结构化脱敏的 JSON/Markdown 摘要，原始联调日志保存在仓库外、限制权限、设置过期删除。

#### AR-R05：远程管理接口没有身份和幂等边界

当前 daemon 的 stdio RPC 信任本地父进程，请求没有客户端身份、能力、管理操作幂等键或审计。直接搬到 SSH/TCP 后不安全。

**要求：**先冻结 Client API C1，引入连接身份、能力、控制租约、`operation_id`、事件游标与审计。

#### AR-R06：UNKNOWN 只有隔离，没有对账和解除流程

`recover()` 会把活跃 Run 变成 UNKNOWN、资源变为 QUARANTINED、任务变为 NEEDS_ATTENTION，但没有完整 API 让用户检查、确认外部副作用、重新绑定原生会话、释放资源或明确失败。

**要求：**实现 Reconciliation 工作流；不允许通过直接改数据库解除。

### P1：进入真实 Harness 前处理

#### AR-R07：普通通知没有收件语义

`notice` 会写入消息表，但不会写 Outbox，也不会进入目标角色下一轮上下文。测试只证明它“不唤醒”，没有证明接收角色之后能看到通知。

**要求：**通知应进入目标角色的被动收件箱；不自动启动模型，在下一次正常 Run 或用户查看时可见。

#### AR-R08：`route_context(section)` 没有真正按 section 过滤

当前实现接受 section 参数，但返回内容未严格按 section 裁剪，而且未完整返回有效项目规则。既浪费上下文，也模糊权限。

**要求：**按 `identity / roles / task / child_results / policy` 分段返回，默认最小化。

#### AR-R09：Schema 与运行时能力不一致

Schema 接受 `git`、`live`、`external`、`artifact`，运行时只真正支持部分输入，输出只允许 artifact。调用者会在“格式合法”后得到运行时不可用。

**要求：**能力协商中精确声明；未实现类型不得在 UI 中呈现为可用。

#### AR-R10：SQLite 版本被精确锁死

当前只允许 `3.53.4`。这能固定开发预览，但未来安全补丁或另一平台打包会被全部拒绝。

**要求：**改为“最低安全版本 + 已验证范围 + 兼容性记录”，未知版本进入诊断模式，而不是永久绑定单一版本。

#### AR-R11：产物引用与保留机制未闭环

数据库有 `artifact_links`，但核心交付路径没有完整维护引用；Git 对象和 worktree 更未实现。无法保证长期可追溯与安全清理。

#### AR-R12：错误被吞掉

Electron 主进程丢弃 Core stderr，对 child error/close 缺少可见诊断，也没有自动重连。远程模式下会造成“界面断开但用户不知道原因”。

#### AR-R13：AuthUnit 配置与实际调度不一致

表中有 `max_active_runs`，实际调度以唯一资源租约强制串行。要么明确 V1.0 固定为 1，要么实现计数租约，不应表面支持多并发。

### P2：UI 和发布前处理

- Renderer 每三秒拉取全量 snapshot，不适合远程与长历史；
- 列表以原始 JSON 为主，尚无产品级对话、时间线和状态解释；
- 目录选择只适用于本机，远程 Linux 项目必须由远程路径 API 选择；
- 关闭窗口只有三种选项，尚缺“当前轮次结束后暂停”；
- 多客户端、只读观察者和控制权冲突未定义；
- 绝对路径和用户名会进入兼容性证据，发布诊断时需脱敏。
