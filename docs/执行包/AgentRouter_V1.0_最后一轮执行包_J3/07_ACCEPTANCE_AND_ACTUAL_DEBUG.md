# 验收与实际调试剧本

## 1. 证据不是测试数量

保留原始 F01—F26、T001—T081 的名称、作用和权威原文；本包 JSON 只提供逐 ID 的归纳索引与执行归属，不覆盖原始详细用例。原文见 [S10](https://github.com/hhhzingy/AgentRouter/blob/62b2e187285aeb0fd73926cdc47c8d830502fb97/docs/执行包/AgentRouter_V1.0功能与开发手册包/04_验收与追踪矩阵.md)。J2 的 46 条独立验收继续保留，见 [S15](https://github.com/hhhzingy/AgentRouter/blob/62b2e187285aeb0fd73926cdc47c8d830502fb97/docs/integration/J2-acceptance.json)，不能被新增测试覆盖掉。

每条验收最终关联：功能/测试 ID → 工作包 → 实现/测试文件 → 受测 commit → 平台与 Harness/账号档案代号 → 操作与预期 → 实际结果 → 脱敏证据/产物 hash → 执行者/用户观察者。

`NOT_RUN` 表示未执行，`BLOCKED_ENV` 表示真实环境或授权不足，`FAIL` 表示已执行且未满足，`PASS` 必须有可定位的实际证据。`N/A` 只适用于某一用例明确不适用于某一组合，并写明理由；不得将完整功能或必选平台整体设为 N/A。发布 JSON 内不得预填 PASS。

## 2. 四类门禁，分别记录

| 层次 | 环境及用途 | 不能替代什么 |
|---|---|---|
| D：确定性回归 | unit/contract/integration/chaos/UI，模拟原生事件与错误注入 | 不能认证真实账号、真实工具进程与原生停止 |
| P：实际进程 | Windows Job / Linux supervisor、真实 SQLite、真实文件、Electron、SSH | 不带实际模型请求的进程测试不能认证 Harness 完整支持 |
| L：真实联调 | 固定版本 Harness + 获准账号/模型 + 正式 Core + 受控临时项目 | 一次成功对话不能代替取消、切号、恢复与业务交接 |
| U：用户现场 | 原生文件选择/保存/IME/托盘、真实任务、费用和结果确认 | 自动注入 OS 对话框返回或 composition 事件不能代替人工操作 |

同一测试可需要多个层次。D 通过、L 未运行时应保留两个子记录，而不是整项写 PASS。

## 3. 受测组合

按本包新范围，Windows Local Core 与 Ubuntu Remote Core 各覆盖 Codex、Kimi Code、pi，共六个组合。每组合至少使用一个实际可用的模型完成三次独立的小文件任务；至少一次角色间交接、一次取消、一次拒绝/限制工具权限、一次会话重新连接/恢复。共享认证单元仍串行，不能为完成“3 并发”放开同份凭据的运行互斥。

Codex/Kimi 的 A→B→A 账号与身份核验需在对应平台完成；pi 至少一项实际 Provider 配置和可得用量验证，不承诺全部 Provider。模型、推理选项和可选原生能力按真实探测呈现；未支持的可选项明确 UNSUPPORTED。任务工具、正确身份、完成屏障、停止和秘密隔离不是可省略的可选项。

数字是本轮新设的最小重复门槛，不是对 J2 已完成次数的描述。真实调用费用由用户批准的预算约束；预算不足就暂停有费用测试，不能伪造结果或无通知切换付费模型。

## 4. 实际可用性主剧本：从空数据到真实交付

使用无生产秘密的临时 Git 仓库，包含一份需求文本和一份可测试小程序。用户批准后，从正式候选包启动，不使用 fixture 标记、测试父 IPC 或开发专用脚本注入角色状态。

### U-01 初次设置

用户在真实界面选择本机或 SSH Core，确认主机/数据集身份；登记临时项目；创建两个协作组、总计三个以上角色。选择真实账号档案、模型与工作区；保存后不自动运行，Bootstrap、用户 PAUSED 意图分别可见。

至少一个角色使用 Codex，一个使用 Kimi Code，一个使用 pi。以自然语言输入需求时可由内部设置 AI 形成 RolePlan 草案，但必须由用户预览并显式应用；不让 AI 自动增加账号、角色权限或任意目录授权。

### U-02 三角色完整交接

角色 A（Codex）接收明确任务：在固定资料基础上写一份实现说明并交给 B。B（Kimi）在独立 worktree 修改一个受控小程序、运行指定测试、登记不可变产物，再通过约定 next_request 交给 C（pi）复核。C 基于冻结输入复核，最终结果只给用户。

检查真实文件与测试输出，不接受只有正文“已经改好”。记录每一段 task_id、binding epoch、原生会话/轮次句柄、result/artifact ID 和 hash；确认 A 不因 B/C 成功产生多余“收到”轮次，C 不在 B 的 HELD/未收尾状态开始。结果交付不等于验收，用户明确接受或驳回。

### U-03 忙碌中的输入与等待

A 忙碌时连续提交三个独立任务，验证 FIFO；再发送明确“补充当前任务”而非新任务，验证输入归属。另一个关联子结果续办只作用于父任务，无关队列不得混进当前上下文。执行一次 route_wait，验证角色不通过无限轮询消耗额度。

### U-04 失败与人工介入

制造一个允许范围内的真实测试失败，结果进入约定问题处理去向；用户选择修复或取消。制造一次“请求已可能发出，但 GUI 未收到响应”的断线，用原 operation_id 查询/核对，不新建任务盲重跑。UNKNOWN 保持可见，只有受信任的原生/进程证据可解除相应资源隔离；人工“我认为没事”不等于受测停止证据。

### U-05 账号与绑定

对临时角色执行账号 A→B→A；旧进程、刷新凭据、受影响角色范围、身份和 epoch 均有核验。再做 Codex→Kimi→原 Codex 的绑定交接，保留旧历史；原生恢复不支持就明确新会话交接，不声称跨 Harness 无损上下文迁移。

### U-06 工作区与组重构

在空闲且无阻断的临时组上实际完成一次 MERGE、一次 SPLIT；用户编辑多个目标和每个角色的映射，明确排队任务、等待依赖、已交付结果和旧历史的处置。Preview/hash/revision 任一过期不得 Commit。故意留下一个活跃 Run 或未核对任务，确认阻断而不是忽略后继续。

### U-07 后台、关闭与 SSH

Windows 本地：关闭窗口选择后台继续，再次打开保持同一 Core 和任务；选择当前轮次结束后暂停，后继任务留队。SSH：退出 GUI/断开 SSH 后 Linux Core 和任务继续，重连从正确数据集及游标恢复；不可将 Windows 本地数据或草稿错投到 Ubuntu 项目。

### U-08 导出、恢复与真实日常任务

下载冻结产物并核对 hash；执行一致性备份，在新的数据目录恢复项目、角色、结果和产物。用户在真实目录/保存对话框点选并取消，使用中文候选窗输入；至少完成一次连续五分钟的不靠开发者指令操作试用，以及一次完整三角色真实任务。记录具体观察，不要求用户只回复笼统“通过”。

最后可在用户指定的 Trassi **隔离副本**进行一个小型、可回滚的实际工作：只读审计或修改一份文档/主机测试文件。不得把 RV1126B SDK、生产唯一副本、板卡烧录、个人凭据用作首次联调对象。

## 5. 故障与压力新门槛

下列是本包对原 T080 等用例补充的操作性门槛；若测量方法需要调整，由 Codex 记录原因并直接向用户确认，不追溯修改失败结果。

| 场景 | 最低方法和门槛 |
|---|---|
| SSH 断开/恢复 | 20 次连接循环，包含至少一次运行中断开、GUI 退出和 Windows 睡眠/恢复；任务不重复、Core 不因单纯 UI 断开退出、事件缺口可解释 |
| 原生进程停止 | 每个平台至少 10 次受控子/孙写进程停止测试；在测试文件上验证停止后无持续写入；不误杀开发 Codex 或用户独立进程 |
| 账号切换 | 每平台 Codex/Kimi 各 1 次真实 A→B→A；每个切换日志阶段至少 1 次非真实秘密的故障注入；刷新凭据测试区分真实刷新与合成重放 |
| 数据恢复 | 本地和远程各 1 次在线备份→新目录恢复→产物核验；候选升级迁移失败→恢复至少 1 次，不能只测试备份文件存在 |
| 负载 | 本地和远程各 12 角色、3 个独立认证单元并发、10,000 条记录；高输出可用 fixture/受控进程产生，报告与真实模型联调分开 |
| 稳定运行 | 本地和远程各 2 小时无真实付费循环的进程/存储/重连测试；另在预算内各 30 分钟混合真实使用，期间不靠重启“恢复正常” |
| GUI 响应 | 在上述负载下，本地交互反馈 p95 ≤ 1 秒；取消请求的“已收到/正在停止”反馈 p95 ≤ 1 秒。模型生成、网络 RTT 和实际停止耗时分别报告，不能混成一个“响应快”指标 |
| 停止超时 | 为每种 Harness 固定可配置软取消宽限和强停止截止（本轮建议 10 秒 + 10 秒）；超过截止仍无资源停止证明，必须 UNKNOWN/隔离，不能显示 CANCELLED 或派下游 |
| 资源稳定 | 记录进程数、句柄/fd、RSS、队列/日志大小。无单调累积的孤儿写进程/句柄泄漏；内存和日志有明确配置上限，压力停止后有恢复数据；不能通过关闭持久性/日志错误抹平指标 |

模型服务偶发限流本身不应被算作产品成功；应验证可解释状态、无重复副作用和恢复。不可控提供商异常的证据与确定性软件缺陷分别记录，前者也不能掩盖用户核心任务仍无法完成的事实。

## 6. 现有与新增命令

下列现有命令来自固定仓库脚本，不是本包发明：

```text
node tools/check-w11.mjs
pnpm spec:check
pnpm doctor
pnpm lint
pnpm db:verify
```

`check-w11.mjs` 会执行合同/冻结/秘密扫描、类型、unit/integration/contract/chaos/UI、B0/W11/J1/J2 Electron 检查。它当前不证明真实 Harness 和 SSH；见 [S08](https://github.com/hhhzingy/AgentRouter/blob/62b2e187285aeb0fd73926cdc47c8d830502fb97/tools/check-w11.mjs)。`doctor` 只说明探测结果，不能把 PROBED 当认证。

本轮要求 Codex 新增统一正式入口，例如 `node tools/check-v1.mjs --profile offline|windows-live|linux-live|release`。**这个新脚本目前并不存在；必须实现并在执行记录中给出真实命令。** 带 live 的模式先检查用户批准记录、预算、秘密隔离与实际环境，无授权不能调用账号；release 模式拒绝缺失的必选用例、不同 SHA 证据及未观察的人工项。

CI 不注入个人账号。CI 负责确定性与打包门禁；个人现场认证在用户机器运行，提交脱敏索引。失败测试不得删除、改成 skip 或用空通过脚本绕过。

## 7. 缺陷闭环

失败 → 最小复现/Issue → 修复提交 → 定向测试 → 受影响公共回归 → 更新实际证据。在 J3-00—J3-12 内循环完成，不在每次成功后停止等网页。每次临时绕过都要记录恢复动作；测试环境被修改后，清理/恢复不能删除用户源文件或无授权撤销用户日常凭据。

发布时，必须同时提交原始 81 项的实际覆盖、J2 46 项的回归/人工补齐、本轮新增矩阵和六组合认证记录；仅有总数不是验收报告。
