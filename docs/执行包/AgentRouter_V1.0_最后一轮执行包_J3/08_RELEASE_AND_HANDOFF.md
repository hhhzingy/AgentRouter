# 正式发布、恢复与直接接管

## 1. 从开发预览到唯一正式入口

当前 `pnpm build:win` 使用旧 Main/Renderer/Core，版本为 `1.0.0-dev.0`；不能将其产物换个名字就当 J2/V1.0。出处：[S07](https://github.com/hhhzingy/AgentRouter/blob/62b2e187285aeb0fd73926cdc47c8d830502fb97/tools/build-win.mjs)；[S18](https://github.com/hhhzingy/AgentRouter/blob/62b2e187285aeb0fd73926cdc47c8d830502fb97/package.json)。

Codex 必须建立唯一正式构建链，统一使用本轮受测 J2 工作台、生产 Core、真实 Adapter、完整迁移、受测平台 helper 和私有运行时。fixture/Mock 仅留在测试入口；正式模式不接受环境变量或父 IPC 绕过真实能力认证。

正式 Windows 交付包含可直接启动的受测便携目录或安装包及清晰入口、版本查询、依赖检测和用户操作手册。完整安装/升级/卸载功能只在已实现并实测时声称；采用便携形态也要完成 T070/T079 对应的部署/更新/移除和源文件保留验收，不能写“便携所以 N/A”。缺少代码签名时明确说明；用户自行决定私用未签名包，不要求全局关闭安全防护。私人仓库 UNLICENSED 状态不授权公开再分发，见 [S20](https://github.com/hhhzingy/AgentRouter/blob/62b2e187285aeb0fd73926cdc47c8d830502fb97/README.md)。

Linux 交付受测 runtime/Core/ssh-bridge/迁移、用户级安装与 service 文件、日志与数据目录说明、启动/停止/状态/升级/卸载命令。操作前打印将写入的位置；不自动重装 Ubuntu、改变厂商 SDK、修改默认 Python、全局 Node、sshd、防火墙或 user lingering。

## 2. 干净环境与分发验证

在新 Windows 用户或干净 VM 完成：没有开发 Node/pnpm/仓库缓存时启动；中文/空格路径；缺 Harness 时明确诊断；用户安装/选择实际 Harness 后完成小任务；真实 OS 对话框、托盘、重新打开、受控退出、账号隔离、SQLite 运行时核验、移除应用保留源项目。新用户环境只证明对应配置，不冒称已覆盖全部 Windows 版本。

Linux 使用用户实际 Ubuntu 20.04 环境以及一个新的数据目录，验证私有 runtime 与原生模块 ABI、UDS 权限、真实进程树停止和服务重启。两端记录 OS/build/架构、可执行文件版本/hash、应用 commit、SQLite 实际版本和工作目录。

所有文件从 clean worktree 和锁文件构建，不依赖未登记的 `.local` 手工补丁。首次取依赖可在用户批准的网络范围进行，固定版本、来源与 hash；不能在启动时追随 latest。

## 3. 数据与升级回退

发布前使用受测在线备份流程，包含数据库一致性快照、schema/config 版本、资产索引/内容及必要 Git 保留引用；凭据与 SSH 私钥不随普通备份导出。恢复到新目录后，验项目/角色/任务/结果/产物 hash、幂等账本与历史，不把未知 Run 自动恢复执行。

备份保护用户内容；默认限制权限、显示内容范围、由用户决定保留与导出。日志转储可能含敏感信息，原始材料留在受限本机位置；Git 中只存脱敏索引。不得用复制单个活跃 `.db` 文件代替一致性备份。

迁移失败必须回到可启动的旧版本 + 匹配数据备份；只回退二进制而继续使用不兼容新数据库不算回退。自定义模型配置、账号引用、工作区路径和本机草稿的升级处理需可解释。卸载不得删除源仓库、工作树和日常 Harness 账号。

## 4. 候选身份与复测

最终代码/测试/打包输入冻结到 `candidate_source_sha` 后重跑正式门禁；每份现场证据同时写这个 SHA 和制品 hash。`evidence_commit_sha` 是后续保存证据的提交，不等于受测源码。新增源码、迁移、配置默认值、依赖或构建逻辑后，生成新候选并重测相关项；最终安全和端到端门禁必须对应新候选。

文档-only 证据提交可单独记录，但必须证明没有改变任何受测输入。合并 main 前，核对待合并树与受测树；合并引入变化就测试合并候选。main 最终 SHA、标签指向、artifact hash 和证据源各自明确，不能混用短 hash。

清单至少记录：版本、source/evidence/main SHA、分支、lockfile hash、编译器/runtime、二进制 hash、schema/protocol revision、六组合认证、测试结果索引、人工验收、备份与回退证据、风险与许可状态。

## 5. 最终发布 Gate

全部满足方可写 `READY_FOR_USER_RELEASE`：

- 原 F01—F25 的所有适用验收通过，F26 外部编排/任意代理仍未开放。
- Windows/Ubuntu × Codex/Kimi/pi 六组合达到本包现场门槛；各自账户、模型、能力边界准确。
- J2 回归保留；原生对话框、Windows 中文候选窗、五分钟试用和完整真实协作由用户观察通过。
- 无消息丢失、身份混用、UNKNOWN 自动重跑、HELD 提前派发、遗留写进程、秘密泄露、版本漂移或核心流程不可用缺陷；核心项无 PARTIAL/BLOCKED_ENV/NOT_RUN。
- 实际包可部署、启动、升级/恢复；备份恢复和数据保留测试通过。
- 原始日志/截图/制品经过脱敏与秘密扫描；已知非阻断限制、运行维护手册、接管项目均落库。

用户对最终候选明确接受后，Codex 直接请求/执行用户授权范围内的 PR 合并、`v1.0.0` 标签和私人 Release。**本包允许准备分支/PR/制品，不代替用户对实际合并、标签和发布的最终确认。** 不 force-push、不移动旧标签、不自动清理旧分支或工作树、不擅自公开仓库/制品。

如果用户暂时不能完成现场授权，状态是 `WAITING_USER`（流程状态），对应测试仍 BLOCKED_ENV/NOT_RUN；不是 V1.0 完成。用户明确削减必选能力时记录范围变更并标明限制版本，不使用完整 V1.0 名称掩盖缺口。

## 6. 直接交接规则

网页端不再是本轮或后续优化的必经审批人。Codex 维护：当前版本/环境、任务板、风险表、兼容性锁、验收记录和维护 backlog。日常修复与优化由 Codex 直接对用户说明目标、影响、测试和结果；无须请用户把报告转交网页端。

仍保留独立代码/安全 Reviewer 和确定性测试。AI Reviewer 可在干净只读上下文中评审实际 diff/证据；不能由作者一句“自查通过”替代，也不能替用户登录或批准扩大权限。多 Agent 根据实际可用模型分配任务，不硬编码未经当前工具支持验证的模型名。

后续可优化：超大项目增量投影、布局细节、快捷键、更多 Provider、可选原生能力、非核心性能体验。**不能推迟到优化：三家真实执行、账号切换、SSH、真实取消/恢复、秘密隔离、worktree、已纳入的组重构、正式包和数据安全。**

最终向用户交付一个报告，包含实际安装路径/启动方法、支持组合、当前账号代号、已跑通的真实任务、恢复/停止方法、已知限制、main/tag/Release/证据链接和维护入口。用户不需从历史聊天推导“怎样启动目前可用版本”。
