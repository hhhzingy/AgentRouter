# AgentRouter V1.0 总协议与工具契约

协议版本：agentrouter/1.0。状态：供实现与验收的规范。只有宿主真正提供对应工具时才能调用，不能仅凭文档宣称消息已发送。

## 1. 适用边界

总协议负责身份、结构、队列、结果路由、版本、记录、运行边界；项目规则由用户或指定 AI 决定业务分工、资料、交付、复核和异常处理。项目规则不能改写总协议的身份来源、回执、幂等、权限或失败语义。

角色 ID 永不复用。展示名可更改。不同项目和协作空间默认不能直接投递。真实发送者由受控桥确定，模型不能填写 from、run_id 或任意 resume_task_id。

## 2. 三种消息

`task.request` 委托明确工作，必须包含任务、输入、预期产物和完成去向。

`task.result` 是某项现有任务的结构化结果，由 route_finish 产生；不是收货回执。

`notice` 供知悉，保存展示但默认不单独唤醒模型。需要行动必须改成明确任务请求。

JSON 结构以 `spec/route.schema.json` 为准。发送者使用 `examples/` 中有效样例；带 `invalid_` 的文件是必须拒绝的反例。

## 3. 请求与完成方式

`to` 指实际执行角色；summary 是动作摘要；body 说明工作；inputs 是引用数组，可为空；expected 列明交付物。完整“谁让谁做什么”由系统用真实身份和摘要组合。

`completion.mode=result` 将结果只投递给 completion.to。目标可为用户或角色，缺失则拒绝，不自动回发起者。

`completion.mode=handoff` 要求交给一个角色承担下一任务。执行者提交结果时必须附完整 next_request，下一请求的目标必须等于原任务约定目标。下一请求必须有自己的产物与完成去向。

`on_problem` 省略时固定为用户。正常交付与异常处理是两条路径；异常不自动抄送所有上游角色。

## 4. 成功静默

route_send 保存成功后仅结束底层工具调用，不新增“已接收”“已开始”“已完成”等业务回执，不单独启动发送者下一轮。当前无其他工作时，发送角色结束本轮等待新输入，不轮询收据。

MCP／pi 工具正常结束仍需最小合法结果；不响应不是静默，而是挂起。需要纠正的格式错误回到当前调用；存储不可写等系统错误返回不同类别，不能假装成功。

artifact 登记返回产物 ID、context 返回角色信息，属于必要业务数据，不受成功回执取消规则限制。

## 5. 完成与收尾屏障

route_finish 只结算当前受控任务。首次提交保存结果、后续消息和 HELD 派发记录，状态为 RESULT_STAGED。原生 RunSettled 和资源核对通过后才释放下一阶段。

结果已保存但原生异常退出时，保留产物并进入核对，不自动发布成功路径。执行者提交后停止修改已交付版本。部分完成、失败、取消不能附成功 next_request，由 on_problem 路径处理。

不要求所有任务都复核；需要复核时用显式任务。Harness 正常退出、结果已读或普通正文“完成了”都不自动等于验收通过。

## 6. 排队与等待

同角色新独立任务 FIFO。当前任务期待的真实关联结果、用户补充可续办当前任务；无关新工作继续排队。续办身份与关联由 Core 推导，不由发送者自填获得优先级。

route_wait 记录 child_results、user_input 或 external_condition，并要求角色结束原生轮次。child_results 只能等待确实回到当前角色／任务的关联子结果；未列 child_task_ids 时指当前已派发并按约定返还的全部相关子任务。依赖失败而结果进入问题中心时，等待不伪装满足，应提示人工处理。

结果先到、等待后提交时，Core 必须检查已存结果，避免丢失唤醒。等待角色不得持续 sleep 或循环调用状态工具。审批等待与业务等待分开，前者通常仍占原生轮次。

## 7. 文件与项目字段

固定 Git 引用使用仓库 ID、完整提交和相对路径；artifact 指向实际冻结内容；live 明确可变；external 只是外部索引，不隐式授权下载或带秘密访问。

Schema 的 maxLength 是字符数；Core 另行执行 UTF-8 字节上限、路径越界、引用存在性和大小校验。哈希不是内容存储。Git 对象需要保留或将交付内容冻结入产物存储。

project_data 是业务扩展区。项目可规定仓库地址、测试类型、报告字段等，但不能通过它更换发送者、创建管理员、启用任意 API 或脚本。规则采用发布修订号，不依赖共享文件被修改后即时全局生效。

## 8. 错误与异常

错误分类为 VALIDATION、AUTHORIZATION、UNAVAILABLE、CONFLICT、AMBIGUOUS。响应包含 code、field、message、suggestion、retryable、trace_id，不包含秘密。

收件角色忙、暂停或限流时可以先保存，不立即向发送角色报格式错误。无法派发、原生失联、身份失效与执行未知进入问题中心；项目明确指定异常处理角色时才调用其业务流程。

同 operation_id 同内容去重；同 ID 改内容拒绝。已知传输失败但是否落库未知时，先用原 ID 核对，不能换 ID 盲目重发。自然语言语义相同的新调用不承诺自动去重。

## 9. 运行与账号

不同角色可并行，但同会话一轮一轮执行，共享工作区写入、命名资源和认证运行单元受控。业务并行声明不等于 OS 隔离。

更换 Harness 或账号前暂停、收尾、保存、核验。旧 binding 保留，epoch 增加；迟到结果不得覆盖新状态。Codex 认证文件不得在相关进程运行时被覆盖。Kimi 跨 Profile 原生恢复失败时明确使用交接新会话，不冒充无损。

## 10. 工具清单与权限

route_context、route_send、route_finish、route_wait、route_artifact_register、route_artifact_read 为本版内部工具。参数遵循 Schema 和 Core 语义校验。

本版不向角色开放 create_role、switch_account、install_plugin 或 arbitrary_api_call。未来外部 MCP／插件需要另行授权并复用相同 Core，不直接修改数据库。

## 11. 协议测试责任

Schema 能验证 JSON 外形，不能单独验证真实角色存在、跨项目权限、产物可读性、父子任务关系、结束屏障与幂等结果。开发者必须把这些检查纳入服务层、数据库约束和故障测试。

正式实现前，`spec/adapter-contract.d.ts` 中的类型是设计契约；不得把它的存在当作实际 Harness 适配已完成。规范与代码不一致时记录 SPEC-CONFLICT，完成一致性修订再发布。
