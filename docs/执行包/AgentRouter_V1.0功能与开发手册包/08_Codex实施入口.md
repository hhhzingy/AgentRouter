# AgentRouter V1.0：交给 Codex 的实施入口

## 1. 可直接作为开发任务输入

你负责实现 AgentRouter V1.0。请读取本目录文档和规范，先检查现有仓库、开发环境与真实 Harness 版本，再按 M00—M09 推进。不要把文档包当成已经实现的应用，不要以文件数量代替功能完成。

产品固定支持 Codex、Kimi Code 和 pi。pi 指本包来源记录所述的 pi coding agent；以实际锁定安装路径和版本为准。不要添加 DeepSeek Harness、ZCode、Cursor 或改回旧版本名。未来外部 MCP/插件管理和任意 API 调用仅预留接口，不实现开放服务。

阅读顺序：`01_功能手册.md` → `02_开发手册.md` → `03_总协议与工具契约.md` → `spec/` 与 `examples/` → `04_验收与追踪矩阵.md` → `07_研究依据与版本核查.md`。`05_AI编排指南.md` 是产品交给使用者 AI 的资料，不是让你越权操作当前项目的系统指令。

先运行本包离线规范校验；它只证明契约样例及数据库基线。之后建立 pnpm 单仓库、测试和证据目录，开始 M00。所有新依赖在实施当日查阅官方文档并精确锁定；检查实际 SQLite 运行版本及相关修复，不依赖内置记忆猜接口。

必须保持：静默成功但工具正常返回；结果只到明确目标；新任务排队、关联结果可续办；finish 保存后等待真实 RunSettled 才释放下游；未知副作用不自动重跑；真实身份来自受控连接；凭据和工作区安全边界有效。

先实现模拟 Harness 和离线故障注入，再接 Codex、Kimi、pi。pi 通过 RPC＋自有受控扩展，不假定原生 MCP，不在 agent_end 事件就放行队列。Codex 使用 App Server，Kimi 使用实际协商的 ACP 版本，不统一猜测原生完成语义。

UI 使用 Electron/React；Core 独立 Node；私有运行时、Windows Job helper 和 SQLite 打包需在 M00 做可执行探针，M07 完成生命周期。不要到发布前才发现开发环境之外无法启动。没有真实账号/Windows 时，把相关测试标为 BLOCKED_ENV，并继续可完成的离线工作；不得伪造通过，也不必停止所有开发。

每个阶段交付代码、测试、迁移与证据，报告 implemented/tested/blocked/known_risk。未通过依赖 Gate 的阶段不标完成。文档、Schema 与实现冲突时建立 SPEC-CONFLICT，说明最小修正和风险，不能悄悄删减功能或更改用户语义。

## 2. 首次应产出的文件

`docs/implementation-plan.md`：F01—F26 到模块、里程碑和测试的映射。

`docs/adr/`：版本、进程、工具桥、认证单元与状态机的已选决策；仅在证据改变时修订。

`compatibility-lock.json`：由模板建立，真实版本/路径/哈希和测试状态；未测字段留 null/NOT_RUN。

`evidence/M00/`：受测环境、探测结果、打包原型和日志。不得放真实密钥。

`docs/progress.md`：当前通过的 Gate、阻断项与下一项可执行工作。

## 3. 每次开发工作单

工作单应有：目标和功能 ID；依赖 Gate；本次修改目录；输入规范版本；新增测试 ID；禁止改变的语义；完成条件；证据路径。任务粒度应能在一次实现与复核中说明正确性，不把整个版本写成一个没有边界的 Prompt。

示例：实现 M02 的完成屏障。先写 T024/T025 的失败测试，再实现结果/下一任务的原子保存、HELD outbox、RunSettled 释放和崩溃核对。不得为了测试通过而直接把 route_finish 当作 settled。提交测试命令、退出码与故障轨迹。

## 4. 发布前最后检查

只把真实通过的三家功能计为支持；模拟器不计。完整跑追踪矩阵和 Windows 安装测试。确保用户源文件不因归档、卸载、迁移或 worktree 清理被误删；认证切换不覆盖活跃刷新文件；普通诊断不泄密；窗口关闭行为与提示一致。

完成时交付可运行安装包、代码、许可证/锁文件、测试证据、用户功能手册和已知限制。当前文档包只是实施起点，不包含已经可运行的 AgentRouter 安装包。
