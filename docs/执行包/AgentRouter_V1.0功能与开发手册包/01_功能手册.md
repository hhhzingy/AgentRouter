## 1. 产品简介

### 1.1 一句话介绍

AgentRouter 是一个本地多 Harness 协作工作台。用户在项目中创建角色，为角色选择 Codex、Kimi Code 或 pi，使它们在各自的会话与工作区中执行工作、传递资料、交接结果，并在一个界面查看协作进展。

Harness 指实际承载 AI 会话、文件工具与执行能力的软件，不是模型本身。一个角色可以使用 pi 作为 Harness，再选择 pi 已配置的某个模型；选择 pi 不代表自动接入所有模型服务。本文的 pi 特指 pi coding agent 项目，不指名称相似的其他产品。[S04][S07]

### 1.2 它解决什么问题

使用多个 AI 工具时，用户常要手工搬运文字和文件、介绍角色背景、确认消息去向，并在不同窗口中寻找当前进展。AgentRouter 把这些协作动作集中起来，使一次任务具备明确的发起者、执行者、输入版本、预期产物和结果接收者。

AgentRouter 不替项目做业务判断。什么工作应该并行、谁来复核、结果是否满足需求，由用户或用户指定的 AI 决定。软件负责执行明确的安排，保存事实，暴露不确定性，而不是猜测项目已经成功。

### 1.3 适用范围

适用于软件开发、资料研究、方案撰写、报告复核、文档整理等能够通过明确输入输出协作的工作。项目可以是 Git 仓库，也可以是普通文件夹。需要强操作系统隔离、无人监管的高风险操作、多人远程共享或跨机器调度的场景，不属于 V1.0 的默认使用范围。

V1.0 以本地单用户、Windows 桌面运行作为发布目标。Linux 通过平台适配接口预留，但不计入本版已支持平台。项目和记录保存在本地，不意味着模型调用离线：角色所需内容仍可能发往相应提供商。

## 2. 核心概念与责任边界

### 2.1 从项目到会话

| 概念 | 面向用户的含义 |
|---|---|
| 项目 | 一组有共同目标和主源目录的工作 |
| Workflow／协作空间 | 项目中的一组角色和协作记录；V1.0 不要求预先绘制流程图 |
| 工作区 | 角色实际读取或修改的目录，可以是主目录、已登记目录或独立 worktree |
| 角色 | 一个持续存在的工作身份，有展示名和不会随改名变化的唯一 ID |
| Harness | 承载角色的 Codex、Kimi Code 或 pi |
| 模型／推理选项 | Harness 实际支持并已配置的模型及其运行选项 |
| 任务 | 一项具有明确要求和交付去向的委托 |
| 轮次 | Harness 接收一次输入后的一段实际执行，不一定完成整个任务 |
| 产物 | 被交接的报告、代码、补丁、数据或检查证据 |
| 绑定历史 | 同一角色曾经使用过的 Harness、会话、账号和工作区记录 |

项目身份不直接等同于绝对路径。目录移动后，应通过重新定位操作更新映射，而不是把历史自动划归一个陌生文件夹。两个项目若指向同一物理目录，软件要识别共享资源，不能因为项目 ID 不同就忽略写入冲突。

### 2.2 谁决定什么

| 问题 | 用户或指定 AI | AgentRouter |
|---|---|---|
| 需要哪些角色 | 提出或确认安排 | 创建并登记真实身份 |
| 谁执行、谁复核 | 制定业务分工 | 按指定 ID 投递 |
| 请求需要哪些信息 | 填充项目实际内容 | 提供固定模板和结构校验 |
| 什么资料是依据 | 确定来源、版本和标准 | 保存、解析支持的引用 |
| 哪些任务能并行 | 判断业务独立性 | 落实队列、工作区和资源限制 |
| 什么算通过 | 解释证据并作出判断 | 记录结论，不伪造验证 |
| 谁能读凭据、扩大目录权限 | 只有用户能授权系统范围 | 执行能力和授权边界 |
| 失败后是否重新执行 | 对不确定副作用作出处理决定 | 保存状态、核对、阻止盲目重跑 |

角色叫“总负责”或“Control”不会自动获得更高系统权限。用户可以指定任意一个 AI 制定协作规则，但 V1.0 实际创建角色、选择账号、扩大系统权限和发布规则，仍通过用户操作完成。

### 2.3 三条使用底线

成功发送不产生额外“已收到”会话；结果只交给任务指定的对象；未知状态不自动当作失败或成功。底层工具仍需正常返回，否则原生 Harness 无法结束该工具调用。这里取消的是业务回执，不是技术响应。[S12]

## 4. 开始使用与环境准备

### 4.1 环境检测

首次进入设置页登记三种 Harness 的实际可执行文件。软件展示检测到的版本、路径、必要环境、登录状态、支持的会话与模型选项。界面区分“检测通过”“未登录”“缺少环境”“版本未验证”和“能力不支持”。

检测通过不等于工作质量通过，也不等于账户永久有效。真正发送任务前仍会检查可用性。检测不得自动升级用户已有工具，不得未经确认修改默认账号配置。

pi 在 Windows 默认使用 Git Bash，当前文档也介绍可选 PowerShell 工具；Kimi Code 的 Windows 指引同样需要注意其 Bash 环境。软件应使用已确认的 Shell 路径，而不是猜测 PATH 中的任意程序。[S08][S27]

### 4.2 推荐的第一次体验

选择临时目录或可恢复仓库，创建一个协作空间，再创建两个角色。先让角色 A 生成一份短文档，完成后交角色 B 检查，检查结论直接发给用户。确认消息去向、产物版本、队列、对话和结果收件箱都符合预期后，再加入并行修改和更多角色。

不要用重要资料的唯一副本验证自动修改、账号切换和强制停止。V1.0 会提供保护和记录，但不是任意命令的撤销系统。

## 5. 项目、协作空间和工作区

### 5.1 项目主页

项目主页应展示项目名、主目录、协作空间、最近活动、运行角色数量和需要处理的问题。用户可以创建、重新定位和归档项目。归档默认停止新派发，保留历史，不隐式删除源文件、原生会话或 worktree。

一个主源目录是项目的入口，不意味着所有角色必须在这个目录同时修改文件。V1.0 可以为项目登记多个工作区，但它们是该项目的执行副本或 worktree，不等于已经实现多主源目录产品能力。

### 5.2 协作空间

空间内可以只有一个角色，也可以有多个。名称可以对应一个目标或持续协作主题。不同空间默认不能互相直接投递；跨空间资料需要用户显式转交。相同主目录下多个空间仍共享物理资源限制。

### 5.3 worktree 操作

对 Git 仓库，用户可以选择已有 worktree，或从明确基础提交创建新的工作区。软件显示关联分支、基础版本、当前修改和目录占用。创建前检查路径；移除前检查未提交修改和未归档产物；存在风险时拒绝自动清理。

Git worktree 共享部分仓库状态，不是完全隔离环境。两个 worktree 中的程序仍可能争用同一端口、数据库或设备。项目规则需要额外说明这些资源。[S20]

非 Git 项目保留普通目录工作模式；软件不应擅自初始化仓库，也不把整个目录复制视为必需前提。

## 6. 角色、模型和独立上下文

### 6.1 创建与命名

用户填写展示名、职责说明，选择 Harness、模型、可用推理选项、账号档案和工作区。系统生成唯一 role_id。不同角色可同名，但界面需要同时显示短 ID 或所在空间，投递始终使用完整身份。

角色职责是长期安排，任务是这一次具体工作。角色不必使用 Planner、Reviewer 等固定名称；“用户选定的规则制定者”也只是一个明确标记，不改变系统授权。

### 6.2 模型选择

模型列表以实际 Harness 返回或其受支持配置为依据。没有推理强度选项的模型，不显示一个无效的“高推理”开关。配置改变应在安全边界生效，并记录在新的运行记录中。

Codex、Kimi Code 和 pi 有不同的模型与配置接口，不能承诺三者的同名档位具有相同含义。[S01][S02][S05]

### 6.3 独立会话意味着什么

每个角色有自己的原生会话、收到的任务和执行历史。它默认不能自动读取其他角色的完整对话。交接必须提供足够的背景和输入引用。

独立上下文不等于完全隔离：工作目录、账号额度、网络和操作系统权限仍可能共享。项目事实应保存在明确版本的文件、产物和已发布规则中，不只存在某个聊天窗口。

### 6.4 更换 Harness 或账号

操作流程为暂停新派发、等到安全边界、保存进展、确认旧执行停止、选择新绑定、加载交接包，再继续。旧绑定不删除，用户可以查看并在以后切回。

交接包包括目标、已批准约束、当前任务、输入版本、已完成产物、未解决事项、下一步和结果去向。恢复旧会话时，补齐暂停期间的变化；不能仅恢复旧窗口就假设它知道最新项目状态。

原生恢复可用时优先使用；不可用时明确新建会话并交接。软件保证保存自己的记录和历史映射，不保证跨提供商迁移隐藏状态、缓存或完整内部上下文。旧会话损坏或原厂格式不再支持时，也不能虚报原样恢复。

## 7. 项目协议与规则制定

### 7.1 三层规则

Route 总协议规定消息类型、身份、投递、状态和固定模板；项目规则规定业务分工、资料来源、产物和复核要求；具体任务单填写本次工作。项目规则可以增加业务字段，不能重写系统身份、绕过权限或要求伪造成功。

用户指定一个 AI 阅读《编排与规则制定指南》，提出角色安排和项目规则草案。用户审阅并发布后，软件生成修订号。旧任务继续引用原修订，除非用户明确暂停并重新安排。

### 7.2 工作区文档

软件在用户同意后，向既有 AGENTS.md 增加受控入口，而不是覆盖整份规范。入口指向总协议、项目规则和角色目录。每个工作区从同一个已发布版本生成镜像；真正的身份注册表由软件管理。

共享文档只介绍角色名单，不写“读到此文件的你就是负责人”。具体身份由软件针对会话注入。Codex 的 AGENTS.md 指令读取有运行边界，不能假设改文件就立即更新所有已有会话。[S13]

## 8. 任务请求、结果与普通通知

### 8.1 发出任务

一项合格请求需要说明：让哪个角色做什么，使用哪些资料，预期返回什么，完成后交给谁，以及遇到问题由谁处理。用户可以通过界面填写；AI 通过实际提供的结构化工具发送，不靠聊天文本中的“交给某某”触发。

发送成功后，不向发送者额外发“Router 已接收”或“对方已经开始”。请求格式有误时，当前工具返回字段位置、原因和修改建议。数据库不可写、权限不足等系统错误会明确区分，不能让 AI 不断改写文字尝试修复系统故障。

目标正在忙或被暂停时，请求可以正常保存并排队；这不是格式错误。排队状态对用户可见，不为此调用发送角色的模型。

### 8.2 两种完成路径

| 方式 | 例子 | 软件行为 |
|---|---|---|
| 直接交付 | 执行者完成后交给用户，或明确返还发起角色 | 仅向约定接收方投递结果 |
| 继续交接 | 执行者完成后交下一角色复核 | 保存本阶段结果，并创建一项明确的复核请求 |

结果接收方不是隐含抄送人列表。角色 A 发起、角色 B 执行、结果给用户时，软件不会再给 A 发完成消息。A 仍可以在用户要求时查相关记录，但不会自动被唤醒。

“交给角色 C”需要区分知悉与行动。希望 C 继续复核，就要给它一张新的任务单，不能只发普通通知并希望它自行猜测。

### 8.3 结果保存后的收尾

执行者提交结果时，软件先保存。涉及下一步的自动交接，在原生轮次确认收尾后才释放；提交成功但执行仍未终止时，显示“结果已保存，收尾中”。若此时进程异常，进入核对，不立刻启动依赖不确定产物的下一阶段。

角色提交结果后应结束本轮，不继续修改已交付版本。软件保留被冻结产物，防止接收方读到后来变化的文件。

### 8.4 部分完成、失败和取消

这些不是成功的变体。结果要说明已做与未做的部分、已发生的文件或外部变化、验证情况和阻塞原因。异常进入约定的问题接收方，默认是用户；不自动沿成功路径交给下一执行者。

### 8.5 普通通知

普通通知用于“供知悉”。它会保存和展示，可在下一次合适输入中提供，但默认不单独启动模型，不要求回复“收到”。需要对方采取行动时，应使用任务请求。

### 8.6 完成与验收

“已交付”表示执行者提交了约定结果；“已确认”表示指定用户或复核角色作出了明确判断。并非所有任务必须复核，但需要复核的任务不能把 Harness 正常结束等同于通过。整个项目的完成标准由项目规则确定，不由软件从若干绿色状态自动推断。

## 9. 排队、等待和多角色并行

### 9.1 同角色新任务排队

同一个角色一次处理一项独立任务。新任务按入库顺序排队；人工补充可选择加入当前任务，或明确创建后续任务。忙碌时不默认插入原生运行流。

一个原生轮次结束，不代表当前业务任务结束。当前任务尚未提交结果也未说明等待时，显示“待明确处置”，后续任务不会擅自取代它。

### 9.2 当前任务需要的结果可以续办

总负责人等待两个子任务汇总时，子任务结果会回到该任务的续办通道，而不是排在无关新请求之后。任务关联由软件维护，不能靠消息正文自称“紧急续办”插队。

负责人如果要求下属把结果直接给用户或第三角色，就不应同时等待那份结果。需要自己汇总，原请求就应指定返还自己。

### 9.3 等待不占着模型空转

角色通过等待操作记录需要的输入，然后结束原生轮次。后续输入到达后再继续。等待人工审批是另一种状态：原生工具可能仍在等待，不能擅自放行第二轮。

长期没有结束的任务可能阻塞队列。用户可以查看原因，选择补充、取消或经确认挂起；软件不从“很久没输出”推断它已经失败。明显依赖环可以提示，但 V1.0 不保证自动解开全部业务死锁。

### 9.4 并行范围

不同角色可以并行。独立 worktree 是代码修改的推荐方式；共享主目录默认限制并发写入。用户可在明确风险后调整限制，软件记录这一选择。

实际并发还受全局上限、工作区、命名资源和账号运行单元影响。同一刷新型认证凭据被多个进程使用未经验证时，采用保守串行；界面应显示“等待账号运行单元”，而不是让用户误以为所有角色天然无限并发。

## 10. 资料索引、版本与产物

### 10.1 支持的引用

| 类型 | 表示什么 | 注意事项 |
|---|---|---|
| Git 固定版本 | 仓库＋完整提交＋相对路径 | 分支名不能独自代表不可变版本 |
| 固定产物 | 报告、补丁等冻结后的内容 | 通过产物 ID 定位，保存完整性信息 |
| 实时文件 | 当前工作区中的某个路径 | 明确可能变化，不能冒充已复核版本 |
| 外部索引 | 仓库地址、资料地址和项目声明版本 | 未解析的引用标注未验证，不自动下载任意地址 |

哈希用于检查内容是否变化，不是内容本身。未提交文件交接前需要实际保存副本。路径应以工作区或仓库为基准，避免把 Windows 绝对路径作为唯一长期身份。

### 10.2 读取与预览

用户可以在消息中打开受支持产物，查看原始来源、版本、大小和关联任务。角色通过工具按索引读取。超大文件、缺失文件、越界路径和不支持的外部来源要明确报错，不悄悄用另一个文件替代。

### 10.3 保留与清理

被历史任务或结果引用的产物不得静默删除。清理需展示影响，备份和保留策略由用户确认。归档角色或空间不等于清除源文件。Git 对象也要有保留依据，不能只记一个提交号就承诺永远可读。[S21]

## 11. 对话页、协作时间线与结果中心

### 11.1 角色对话页

在 AgentRouter 内点开角色，可以查看用户输入、接收任务、AI 输出、工具活动、审批请求、产物和收发消息。无需为日常查看不断打开原厂窗口。

展示的是协议提供且软件实际记录的内容，不保证与原厂 UI 每一个组件相同。历史导入或回放不能再次执行旧工具调用；从未收到且无法补取的记录应标明缺口。[S01][S02][S05]

用户可以发送消息、选择加入当前任务或排入新工作、暂停后续任务、申请中断。原厂和 AgentRouter 不应同时控制同一个原生会话；辅助打开原厂查看不自动构成双向实时同步。

### 11.2 三种状态不能混在一起

| 状态层 | 用户看到的例子 | 数据依据 |
|---|---|---|
| 投递 | 已保存、排队、投递中、待核对 | Route 消息记录 |
| 执行 | 执行中、等待审批、正在收尾、已停止 | Harness 事件与进程状态 |
| 业务 | 等待输入、已交付、待复核、失败 | 任务、结果及明确验收 |

协作时间线显示“角色 A 让角色 B 复核报告，并交给用户”。这描述任务意图，不证明 B 已经开始；实际状态另行展示。

### 11.3 用户收件箱与问题中心

收件箱集中展示约定交给用户的结果，支持查看来源、输入与产物版本、证据、限制和相关对话。标记已读不是验收；确认、驳回或后续任务需要明确操作。

问题中心集中展示登录失效、资料缺失、不可投递、权限请求、限流、恢复核对和工具崩溃。查看问题可以定位到角色、任务和执行轮次。默认不为每条系统状态调用 AI。

## 12. 账号、额度与提供商

### 12.1 Codex

V1.0 支持登记用户有权使用的账号档案，展示可查询的身份与额度，并在安全边界通过替换专用运行目录内 auth.json 切换账号。文件凭据与系统凭据库是不同后端；只在已验证的文件后端下执行替换。[S14]

切换前显示受影响角色，用户可选择等待、手动关闭相关客户端，或允许软件关闭明确归属的受控进程。未确认旧运行停止时不替换。软件不按程序名结束用户所有 Codex，也不默认覆盖用户日常默认目录。

切换时保留旧账号最新刷新后的凭据；启动后核验实际身份，再恢复会话。文件存在或文件名正确不是身份验证。官方认证维护说明也提醒避免并发共享认证副本，以及用旧副本覆盖刷新后的文件。[S15]

### 12.2 Kimi Code

V1.0 支持按账号 Profile 管理受控配置空间，查询可用身份与额度，在安全边界更换绑定。它不是照搬 Codex 的文件格式，不应假设两家都有可直接互换的 auth.json。

旧账号会话与记录保留。切换后优先使用经验证的原生恢复方式；跨账号空间无法原样加载会话时，明确提示将新建会话并加载交接包，用户确认后继续。不能静默声称上下文无损。

额度接口存在业务层错误包装；查询失败时保留最后成功时间并显示未知或过期。查询与运行可能涉及相同凭据刷新时，等待安全窗口，不为了刷新额度打断正在工作的角色。[S03][S28]

### 12.3 pi

pi 的 Harness 与模型提供商需要分别显示。V1.0 读取已配置的提供商、模型及认证状态，使用用户选择的受控配置；不自动继承所有环境变量中的秘密，也不导入未经信任的扩展。

能取得 token 或费用统计时展示来源和时间，但这不等于某个订阅的剩余额度。V1.0 不承诺所有 pi 提供商的统一余额查询或通用自动切号。pi 和 Codex 即使使用同一类模型，也不是同一个原生会话。[S07]

### 12.4 额度的统一表达

界面显示账号、产品、窗口、已用量或剩余量、重置时间、查询时间和状态，不把所有资源压成一个无来源百分比。同账号的多个角色共享的额度，不重复显示成每角色独立余额。

本版不根据额度自动跨提供商迁移任务。授权范围和资料允许发送到哪里，比剩余额度更优先。任何账号功能都只服务于用户合法持有的账号和正常配额使用。

## 13. 暂停、停止、后台继续与限流

### 13.1 暂停和取消不同

暂停新派发保留队列，已经运行的轮次按既定方式收尾。取消当前执行则向 Harness 请求停止，并核对工具与子进程状态。取消不保证撤销已写文件、已发送邮件或其他外部副作用。

对某个角色暂停时，其他角色仍可把消息保存给它，等待恢复。暂停空间或项目时影响其新派发，不删除任务。

### 13.2 关闭操作

| 操作 | 影响 |
|---|---|
| 关闭角色标签页 | 只关闭查看页面，角色不停止 |
| 关闭主窗口并后台继续 | 主进程、Route Core 和 Harness 连接留在托盘运行 |
| 当前轮次结束后暂停 | 当前运行收尾，禁止新轮次；不等于整个业务任务完成 |
| 停止并退出 | 保存、取消与核对受控进程后退出 |

重新打开窗口应恢复展示，不重新启动已在运行的任务。只留下 Harness、完全退出 Route，不属于本版支持的持续协作方式。托盘后台也不意味着关机、注销或系统休眠后模型持续工作。[S18]

### 13.3 自动接力限制

用户可以配置每个角色在短时间窗口内的自动唤醒次数、空间较长窗口、总并发数和单条协作链的累计预算。时间窗口防止短时爆发，累计预算防止低频但永不结束的循环。

达到限制后消息仍被保存，新的自动工作暂停，用户可查看原因并决定继续。停止、结果保存和错误记录不被这一限制阻断。重启不会清空已经消耗的预算记录。

## 14. 稳定性、备份和恢复

### 14.1 本地持久化

消息、任务、角色绑定和关键状态保存在本地 SQLite；文件产物单独保存并建立引用。成功提交后不只停留在内存里。数据库应位于软件的本地数据目录，不放到网络共享或随源代码同步的位置。[S16]

### 14.2 崩溃后的表现

已保存但尚未派发的工作可以继续排队；可能已被 Harness 执行却没有最终确认的工作显示待核对；已经保存的结果不会因 UI 关闭消失。恢复过程不以“最后没看到回复”为依据直接重做。

用户在问题页查看最后事件、实际文件和已交付产物，再决定重试、确认、取消或重新安排。软件应清楚说明哪些恢复是自动完成，哪些依赖人工判断。

### 14.3 备份与导出

支持导出协作记录和脱敏诊断包，支持一致性备份及恢复演练。普通备份默认不包含账号明文凭据；因此恢复到另一台机器时，可能需要重新登录或由用户另行安全迁移认证。

备份不等于整个源仓库副本。备份范围应明确列出控制数据库、项目规则和受管产物是否包含；原始工作目录、外部服务状态和账号需要另行处理。SQLite 运行中不能只复制一个主数据库文件冒充一致性备份。[S22]

## 15. 安全与使用限制

业务角色约定不等于操作系统沙箱。共享同一 Windows 用户权限的工具仍可能访问用户能访问的资源。V1.0 应避免把凭据、控制数据库和桥接令牌放进项目或 Prompt，并限制自身接口，但不宣称能够抵抗同一系统账号下的恶意程序。

pi 的扩展是可执行代码，不是纯文本配置。V1.0 只自动加载随软件审查并固定的 Route 桥扩展；其他扩展需用户明确信任。pi 的工具确认和项目信任，也不等价于完整文件／网络隔离。[S04][S06]

对话中的网页、代码注释和外部文件是资料，不获得改变系统授权的资格。模型要求安装额外程序、访问外部服务或执行高风险操作时，按可用审批能力处理；不能因为它自称负责人而批准。

若某 Harness 无法提供项目要求的强制权限能力，应拒绝该配置或明确使用较弱的、用户同意的受信模式，不能静默降级。V1.0 不面向敌对代码的安全执行环境。

## 16. 常见故障与处理

| 现象 | 可能含义 | 推荐操作 |
|---|---|---|
| 发送后没有收到确认消息 | 成功回执被设计为静默 | 查看时间线，不重复派发 |
| 角色一直显示排队 | 当前任务、工作区、账号或预算占用 | 查看具体等待原因 |
| 角色说完成，但没有结果 | 只生成了普通文字，没有结构化交付 | 要求补充正式结果或人工处置 |
| 结果已保存但未交接 | 原生轮次仍在收尾，或需要核对 | 不手动重复发同一任务 |
| 下属结果回不来 | 原任务的去向不是当前角色，或关联有误 | 检查任务单和完成约定 |
| 额度显示未知 | 接口不可用、账号不适用、待安全窗口或查询失败 | 查看时间戳，避免推断为零或无限 |
| 更换 Harness 后背景不全 | 原生上下文不能自动跨工具迁移 | 使用交接包补足版本和进展 |
| 已取消但文件仍变化 | 子进程尚未停止或存在外部执行 | 暂停冲突工作，核对进程和产物 |
| 崩溃恢复后要求人工处理 | 无法证明副作用是否已经发生 | 先查文件与记录，再决定是否重试 |
| 原厂历史与 Router 展示不同 | 能力差异、未观察到的数据或非 Router 创建会话 | 查看历史范围与缺口提示 |

## 17. 默认值与边界设置

以下是供开发与测试的起始默认值，不是性能承诺：全局同时运行 3 个角色；单角色 60 秒内最多 5 次自动启动；单空间 300 秒内最多 30 次；单协作链 100 次或 8 小时后暂停新自动工作。用户可调整，软件记录调整。

单个消息正文建议上限 64 KiB，整体信息包 256 KiB；受管产物默认单文件上限 20 MiB，超过时要求改用受支持存储方式。大日志应分页或产物化，不无界塞入下一角色上下文。这些上限可配置，但核心必须拒绝超限而不是截断后假装完整发送。

对自动重试和无输出超时采用保守策略。长时间无新事件只触发提示或核对，不直接重做文件操作。模型 token 上限与费用预算以 Harness 能力为准；不能提供看似精确但无可靠数据来源的费用硬上限。

## 18. 三个典型协作场景

### 18.1 执行、复核、直接交给用户

用户指定角色 A 规划。A 给 B 派执行任务，要求完成后交 C 复核。B 冻结结果并创建给 C 的复核请求；C 把结论交用户。A 不接收无意义回执，用户在时间线看全链路。

### 18.2 两项独立工作并行、负责人汇总

A 发出两项任务，分别交 B、C，在独立工作区执行，结果都指定回 A。A 记录等待并结束轮次。结果逐步入库后，A 按关联输入续办；收齐后提交汇总。无关新任务不抢走 A 的当前职责。

### 18.3 关闭窗口后继续协作

B、C 正在工作，用户关闭主窗口并选择后台继续。托盘显示运行数量。出现审批时等待用户。重新打开窗口后恢复同一任务和对话，不重新派发。选择“当前轮次结束后暂停”则阻止后续接力，即使当前结果已经保存。

## 19. 功能验收与非承诺

验收应证明三家 Harness 在已锁定版本中完成创建、调用、工具桥、取消、状态、历史和结果交接；还要证明格式错误可修正、成功无额外回执、结果不隐式抄送、同角色队列正确、跨角色并行真实、文件版本明确、崩溃不盲目重跑。

V1.0 不承诺 AI 总能遵守业务规则、不承诺所有外部副作用只发生一次、不承诺原厂 UI 完全同步、不承诺账号切换绝不需重新登录、不承诺任意文件操作可撤销。软件需要把这些限制转成可见状态和可处理流程，而不是隐藏起来。

本手册与《开发手册》一起构成 V1.0 功能基线。实现时发现原厂能力与文档不同，应提交差异和证据；不能擅自删减功能，也不能用模拟数据标记真实接入已经通过。

## 20. 文档包与术语

《开发手册》用于实现；《总协议》与 JSON Schema 用于消息校验；《AI 编排指南》和项目模板用于制定业务协作；《验收与追踪矩阵》连接功能、里程碑和测试；《Codex 实施入口》给实现 AI 明确开始方式。

Durable 表示已保存并可恢复的状态，不表示 AI 自动记住；幂等表示同一操作的安全重复处理，不是语义相似任务自动合并；worktree 是工作树，不是模型或沙箱；MCP 是工具交互协议，ACP 是客户端驱动 Agent 的协议，二者都不是项目流程引擎。
