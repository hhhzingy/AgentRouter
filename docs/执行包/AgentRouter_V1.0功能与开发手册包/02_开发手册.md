## 0. 实施入口与文档权威

先读《功能手册》确定用户行为，再读本手册、`spec/`、`04_验收与追踪矩阵.md` 和 `08_Codex实施入口.md`。名称固定为 AgentRouter V1.0，适配器枚举仅为 `codex`、`kimi_code`、`pi`。不把 DeepSeek Harness、ZCode 或 Cursor 写进本版支持清单。

本文采用 MUST／SHOULD／MAY 表示必须、建议和可选。机器规范仅定义外形与可自动验证的约束；业务语义、权限和状态转移仍由 Core 验证。发现文档、Schema 和代码不一致时，先建立 SPEC-CONFLICT 记录并定位影响，不能挑最容易实现的一项静默覆盖。

`spec/` 是可验证的协议和数据库基线，不是完整应用代码。附带检查证明示例、语法及部分约束一致，不证明原生 Harness 行为、Windows 进程管理或断电持久性已经通过。所有生产能力必须通过本手册的阶段 Gate。

## 1. 总体判断与明确决策

### 1.1 可行性结论

核心功能技术上可实现。Codex 有官方 App Server；Kimi Code 提供 ACP；pi 提供 RPC 和扩展机制。三者都存在程序化控制路径，因此无需把桌面点击或终端文本抓取作为主链路。[S01][S02][S04][S05][S06]

最大风险不是“能否发一条 Prompt”，而是工具桥身份、轮次结束语义、外部副作用的不确定性、账号刷新并发、Windows 进程树，以及不同版本行为变化。V1.0 选择确定性 Core、单数据库写者、受控进程和严格能力清单，减少这些风险的传播。

### 1.2 决策摘要

| 决策 | 选择 | 理由与边界 |
|---|---|---|
| 产品对象 | 项目→协作空间→逻辑角色→绑定历史 | 角色不等于原生会话 |
| 业务组织 | 用户或指定 AI 制定 | 不实现自动规划引擎 |
| 执行内核 | TypeScript 确定性状态机 | 不调用 LLM 判断路由和事务状态 |
| 持久化 | 本地 SQLite＋不可变产物存储 | 不引入分布式消息系统 |
| 跨 Harness | 原生协议分别适配 | 不强迫 pi 使用 ACP 或原生 MCP |
| 主接入 | Codex App Server；Kimi ACP；pi RPC＋受控扩展 | 不改原厂私有数据库 |
| 成功回执 | 无业务回执，合法最小工具结果 | 不能故意挂起 RPC |
| 结果路由 | 只到指定对象；交接显式新请求 | 不默认抄送发起者 |
| 队列 | 每角色一个独立任务，续办独立关联 | 避免返回结果被无关新任务挡住 |
| 并行 | 不同角色和工作区可并行 | 会话、凭据和共享写资源另行限制 |
| 账号切换 | Codex 受控换 auth；Kimi Profile 绑定切换 | 不做热覆盖或无损承诺 |
| 生命周期 | 窗口可关，主控和 Core 保留托盘 | 不承诺完整退出后继续协作 |
| 外部扩展 | 核心服务接口与权限预留 | 不开放外部编排 MCP／通用 API 代理 |

### 1.3 哪些是已核实事实，哪些是待验证假设

已核实：三家接口入口、pi 的扩展与 RPC 消息类别、Kimi 的能力协商和额度接口、Codex 的文件凭据模式、SQLite 的事务与 WAL 限制。来源见第 29 章及独立来源文件。

待验证：用户安装版本的具体方法与字段、模型选项、原生会话在账号或版本变化后的恢复、同一认证运行单元的安全并发、工具桥与批准路径，以及打包后的 Windows 路径和进程树。代码必须记录这些验证结果，而不是把本文中的路径示例视为环境已存在。

## 2. 质量目标与非目标

### 2.1 必须保持的系统不变量

I01：一次已成功持久化的消息不会因 UI 关闭从队列消失。

I02：同一 `operation_id` 和同一请求内容只能产生一个逻辑写操作；同 ID 不同内容返回冲突。

I03：同一角色、原生会话最多一个受控运行；关联续办与独立任务明确区分。

I04：结果只按完成约定投递，发起者不是隐含抄送人；系统状态变化不自动调用模型。

I05：`route_finish` 保存结果不立即等于可派发下一阶段，必须通过原生收尾屏障。

I06：身份、项目范围、任务上下文和绑定代次来自受控连接，不信任模型自报。

I07：活跃旧进程没有确认停止时，不把其工作区写入权转给新绑定。

I08：不确定的外部执行不自动重跑；过期结果不能覆盖当前状态。

I09：产物内容先可靠存在，再提交数据库引用；固定版本不悄悄解析为最新版。

I10：原生结束不等于任务完成，任务完成不等于业务验收通过。

I11：取消不宣称撤销已发生副作用；后台模式不绕过人工审批。

I12：账号凭据、桥接令牌不进入 Prompt、源仓库和普通诊断包。

### 2.2 性能与规模起点

建议认证测试基线为一个 Windows x64 本地用户、12 个登记角色、默认 3 个并行运行、10,000 条历史消息和大输出流。它是测试规模，不是对任意电脑的容量承诺。目标是在指定测试机上，纯本地有效发信持久化 p95 不超过 250 ms，10,000 条队列／记录下列表操作不冻结界面，持续输出下停止按钮仍能工作。外部模型延迟不计入本地 SLO。

代码应记录测试机、磁盘类型、依赖版本和真实测量结果。未达到目标时先定位瓶颈，不通过降低持久性或丢弃关键记录“达标”。

### 2.3 威胁模型

V1.0 管理可信本地用户选择的 Harness，保护软件接口与敏感信息的正常使用边界，不承诺抵抗同一 Windows 用户下的任意恶意进程。命名管道或随机 token 不能把一个拥有同用户完整文件权限的恶意 Agent 变成受沙箱限制的程序。

外部资料、模型输出和项目脚本均不得改变系统权限。若用户需要强隔离，必须另行提供受测 OS 沙箱；V1.0 在该能力不存在时明确显示不支持。不能把 Prompt 中的“只读”或 pi 的项目信任开关包装成安全沙箱。

## 3. 技术栈与运行时策略

### 3.1 选定的基线

前端为 React＋TypeScript，桌面壳为 Electron，Core 为独立 Node.js 进程，存储为 better-sqlite3 驱动的 SQLite，协议为 JSON Schema Draft 2020-12＋Ajv 校验。使用 pnpm workspace 组织单仓库，Vitest 做单元与组件测试，Playwright／Electron 驱动做桌面端到端测试。具体包版本在 M00 核查后精确锁定，不在运行时追随 latest。

Node 24 当前属于 LTS 分支，可作为 Core 候选基线；其精确补丁版本、Electron 版本和 SQLite 驱动都要通过锁定与安全检查。[S23]

### 3.2 为什么将 Core 放到独立 Node 进程

UI 渲染、同步数据库访问、大日志处理和 Harness 协议不应全部挤在 Electron 主进程。独立 Core 提供可测试的无界面入口，也便于未来被外部插件调用。窗口崩溃不会自动等于 Core 工作结束，但主进程完全退出仍按受控退出处理。

开发阶段可使用显式配置的 Node 24 路径；Windows 发布包应附带经校验、固定版本的私有 Node 运行时，用同一运行时执行 Core 和内部 MCP 桥。构建时保存下载来源、SHA-256 和许可证，不在用户启动时自动下载运行时。这样不依赖 Electron 的 RUN_AS_NODE 模式，也避免把“本地开发能跑”当作打包完成。

SQLite 原生模块在私有 Node 的 ABI／N-API 环境中加载，不在渲染进程加载。better-sqlite3 的当前发布说明已有 N-API 迁移，但仍必须验证实际打包版本与 Windows 二进制，不假定理论兼容即已通过。[S24]

### 3.3 版本管理要求

建立 `compatibility-lock.json`，记录应用协议、可执行文件路径与哈希、Harness 版本、Node／Electron／驱动／SQLite 实际版本、探测能力、原生协议版本、测试时间和证据位置。源码文档的观察版本不等于本机验证版本。

SQLite 运行时启动时执行 `SELECT sqlite_version()`，检查 WAL-reset 修复：新构建应使用包含修复的受测版本；官方列出 3.51.3 及以后和部分回移修复版本。不能只按“SQLite 主版本够新”或 npm 包名判断；还要排除已撤回或未认证发行版。[S16]

## 4. 仓库结构、进程与通信

### 4.1 推荐目录

```text
apps/desktop/              Electron 主进程、preload、React
apps/core-daemon/          Node Core 入口、IPC 与内部服务
packages/protocol/         Schema、类型、错误码与版本
packages/domain/           纯领域状态与不变量
packages/storage/          SQLite 仓储、迁移、备份
packages/runtime/          调度、outbox、恢复、资源与限流
packages/adapters/codex/
packages/adapters/kimi/
packages/adapters/pi/
packages/role-bridge/       Codex/Kimi 内部 MCP bridge
packages/pi-extension/      pi 专用 Route 工具扩展
packages/artifacts/        产物冻结、Git、路径解析
packages/accounts/         档案、凭据切换、身份与额度
packages/platform/         Windows 与未来 Linux 边界
native/windows-supervisor/  受控进程 Job Object 小型辅助程序
resources/protocols/        总协议、项目与角色模板
fixtures/                  原生事件与协议样本
 tests/                    单测、契约、故障、桌面与打包测试
 docs/                     设计决策、验证结果和操作说明
```

目录只是建议；依赖方向必须保持：UI／桥／适配器使用 Core 应用服务，Domain 不依赖 Electron 或 Harness SDK，角色桥不能直接写数据库。

### 4.2 进程分工

Electron Main 负责窗口、托盘、用户授权界面和启动 Core；Core 是唯一控制数据库写者，管理任务与适配器；各 Harness 是独立进程或经过验证的原生运行单元。MCP bridge 与 pi extension 只转换调用并附加受控身份，不自行调度其他角色。

Electron 渲染层通过明确的 preload API 调主进程，再经 IPC 调 Core。禁止向页面暴露任意文件读写、任意进程执行或通用 IPC method 名称。[S19]

### 4.3 内部工具通道

Core 可以在 `127.0.0.1` 的随机端口开放内部角色调用端点，使用每绑定的短期 Bearer 凭据、请求体上限和作用域校验。仅该端点供 bridge／pi extension 使用；角色创建、账号切换、授权发布等管理服务只经桌面 IPC，不挂到这个 HTTP 端点。

限制 Host 和 Origin；不开放 CORS；拒绝浏览器跨域请求；不在命令行、日志、Prompt 或项目文件展示凭据。通信 token 的保护是防止误用与跨角色混线，不是抵御同用户恶意进程的安全证明。

生产端点名称与传输可在 M00 改为命名管道，但必须记录 ADR，并让 Core 服务契约保持不变。不得同时维护两套不同的路由规则。

## 5. 领域模型、身份与上下文

### 5.1 数据对象

Project、Space、Workspace、Role、Binding、Task、Message、Run、Artifact、PolicyRevision、AccountProfile、AuthUnit、Approval、Issue、ChainBudget 是本版主要对象。完整字段和约束见 `spec/schema.sql`，不要在 UI localStorage 再维护另一份任务真相。

ID 使用带类型前缀的 UUID 等不可复用随机标识。展示名可变，ID 不可改派。存储时间用 UTC epoch 毫秒，界面按用户时区显示；活进程的超时使用单调时钟。序列排序以数据库分配的单调序号为准，不信任消息内自报时间。

### 5.2 角色与绑定

Role 是长期身份；Binding 记录 Harness、原生会话定位符、模型、账号、工作区、能力快照和递增 epoch。一个角色只允许一个 current binding。更换会话不覆盖历史记录。

任务发出时记录项目规则修订、完成约定和目标角色；执行时记录真正选用的 binding／model／auth unit。若排队期间角色更换工具导致提供商或权限范围变化，派发前重新检查，必要时要求确认；不能把旧授权默默扩大到新服务。

### 5.3 三种上下文

第一层是已发布项目记录与产物；第二层是当前任务包；第三层是原生会话历史。Core 按需提供身份、规则版本和输入引用，不每轮注入整个项目历史，也不默认提供其他角色私有对话。

交接包是有版本的可读文档和产物索引，不是 hidden state 迁移。切回历史会话时依据 `last_synced_policy_revision` 与工作进展补充变化；无法重放则新建明确标识的会话。用户必须能区分“恢复原生会话”与“基于交接建立新会话”。

## 6. 总协议、项目规则与工具契约

### 6.1 固定协议

协议标识固定为 `agentrouter/1.0`。消息三种：`task.request`、`task.result`、`notice`。模型的请求体不得包含可伪造的 `from`、`project_id`、`run_id`、`resume_task_id`；这些由 Principal 和运行上下文填入。

完整 Schema 见 `spec/route.schema.json`。核心字段严格 `additionalProperties:false`，项目扩展仅允许放入 `project_data`。项目规则的声明式校验仅支持有限字段类型、required、枚举、长度等白名单，不执行项目提供的任意脚本，不允许远程 `$ref` 或无界正则。

### 6.2 内部角色工具

| 工具 | 输入 | 输出和作用 |
|---|---|---|
| route_context | 可选的受限查询范围 | 当前身份、有效角色、工作区、任务、规则与关联结果 |
| route_send | request 或 notice | 持久化成功时最小技术结果；错误返回修正信息 |
| route_finish | outcome、summary、body、outputs、可选 next_request | 保存结果与待释放后续消息；不得结算其他任务 |
| route_wait | waiting_for、reason、可选已关联等待对象 | 记录当前任务等待，角色结束本轮 |
| route_artifact_register | 受管工作区内路径及冻结选项 | 返回工作必需的产物 ID、大小、哈希 |
| route_artifact_read | 引用、受限范围或分页 | 返回内容或可明确解释的读取错误 |

查询或登记工具返回业务必需数据，不属于应取消的成功收货回执。`route_send` 成功不主动返回冗长的“已收到／已开始”，不再向发送角色排一个回执轮次。底层 MCP 工具仍返回合法结果；客户端不兼容空 content 时用最小机器结果并记录兼容策略。[S12]

### 6.3 任务请求最小内容

必须有收件角色、动作摘要、工作说明、输入列表（可为空但必须显式）、预期产物、完成方式和目标。`on_problem` 未指定时固定为用户。样例文件中的角色与产物只是示例 ID，不声称环境已存在。

`completion.mode=result` 将结果直接投递给明确用户或角色。`mode=handoff` 要求执行者提交下一张完整 task.request，目标必须匹配已约定角色。Core 不解释自然语言 if／else，也不擅自生成复核标准。

### 6.4 结果与通知

`task.result` 由 `route_finish` 生成，不能从 route_send 伪造。正常结果不抄送发起者。返回角色没有关联活动任务时，结果进入普通待处理输入队列；没有新独立任务的情况下处理这份结果，不要求答谢。

notice 仅存储展示，并可作为下一次输入的有界背景。系统错误也不应伪装成需要 AI 反复回复的 notice。真正要求处理问题时，由显式异常策略产生任务或进入用户问题中心。

### 6.5 错误契约

返回 `code`、`category`、`field`、`message`、`suggestion`、`retryable` 和非秘密 trace ID。区分 VALIDATION、AUTHORIZATION、UNAVAILABLE、CONFLICT、AMBIGUOUS。目标忙碌和限流属于已保存等待，不是格式错误。

同一个 operation_id 的传输重试可以安全重复；修正过内容的新工具调用必须换新的操作身份。不能在看到 `STORE_UNAVAILABLE` 时建议模型修改业务措辞。

## 7. 状态机与完成屏障

### 7.1 状态分层

| 层 | 状态示例 | 不能混淆的含义 |
|---|---|---|
| 消息投递 | STORED、HELD、QUEUED、DISPATCHING、DELIVERED、UNKNOWN、UNDELIVERABLE | 投递成功不是工作完成 |
| 原生 Run | CREATED、STARTING、RUNNING、WAITING_APPROVAL、SETTLING、SUCCEEDED、FAILED、CANCELLED、UNKNOWN | 原生正常收尾不是业务达标 |
| Task | QUEUED、ACTIVE、WAITING_INPUT、RESULT_STAGED、DELIVERED、HANDED_OFF、PARTIAL、FAILED、CANCELLED、NEEDS_ATTENTION、SUSPENDED | 结果交付不是整体项目验收 |
| 用户验收 | NOT_REQUIRED、PENDING、ACCEPTED、REJECTED | 由明确验收者作出，不由 LLM 调用退出码推断 |

SUSPENDED 表示用户显式挂起未结束任务，不是完成；已确认原生停止和资源释放后才允许另一个独立任务占位，恢复该任务需再次排队和检查上下文。业务终态与原生 Run 的清理状态分别保存。UI 可以展示“已保存结果／仍收尾”，不强迫一个状态字段同时表达两种事实。

### 7.2 `route_finish` 采用两阶段本地发布

第一阶段：校验执行者和 epoch；固定产物；在同一数据库事务保存 result、下一阶段 request（如有）、outbox，标记 HELD；Task 进入 RESULT_STAGED；工具正常结束。

第二阶段：收到经过验证的 RunSettled，确认没有遗留批准或受管写入，原子释放该 Run 对应 outbox，推进 Task，释放角色执行位置。随后才允许依赖本结果的新任务派发。

这样避免执行者刚提交结果，原生 Harness 却仍在工具循环中修改文件，下一角色已基于半收尾状态工作。它不是分布式两阶段提交，只是本地保存和派发屏障。产物不可变仍是必须条件。

若 Run 在第一阶段之后异常退出，保留结果，转 NEEDS_ATTENTION，outbox 仍 HELD。用户核对后可以选择发布既有固定产物或重做；不得删除结果，也不得默认继续成功路径。

### 7.3 部分结果和取消

partial／failed／cancelled 不自动进入成功交接路径。向 `on_problem` 保存实际已完成产物，相关输出的发布仍需核对原生副作用；紧急问题可先在用户问题中心显示，不必等待成功屏障。

模型在普通正文说“完成了”没有调用 finish 时，Run 结束后 Task 进入 NEEDS_ATTENTION，不自动追加无上限的纠正轮次。用户管理对话和结果处理轮次可以没有业务 Task，正常结束即回空闲，不强制创建永远未完成的“负责人任务”。

## 8. SQLite、事务与备份结构

### 8.1 存储设置

Core 独占数据库写入口；单个长期连接处理短事务。启动设置外键、WAL、关键持久化 FULL、受控 busy timeout，执行兼容版本与迁移检查。不要把网络调用、LLM 调用或等待用户批准放在数据库事务里。[S16][S17]

SQLite 修复要求由实际运行时版本验证。系统测试也要覆盖驱动打包与 checkpoint，而不是仅用开发机的系统 sqlite 工具代替测试。

### 8.2 关键事务

| 操作 | 必须一起提交的记录 |
|---|---|
| 发任务 | operation ledger＋message＋task＋outbox＋事件 |
| 完成并交接 | result＋下一 request/task＋HELD outbox＋任务状态＋事件 |
| 获得执行权 | role slot＋Run＋资源占用＋派发意图＋预算启动记录 |
| 绑定切换 | 新 binding／epoch＋旧绑定封存＋审计 |
| 发布项目规则 | 不可变修订＋有效修订指针＋事件 |
| 人工核对结果 | 核对决定＋结果发布或终止＋审计 |

`operation_id` 的唯一键需包含可靠 Principal 范围；存入请求规范化摘要。事务失败不留下半创建任务。请求去重的持久性与 outbox 的发送记录分别管理，不能只用内存 Set。

### 8.3 附带数据库基线

`spec/schema.sql` 给出实体、外键、枚举和关键唯一索引。跨表业务约束由服务在 `BEGIN IMMEDIATE` 等短事务中检查；SQL 约束是第二道防线，不代替状态机。所有 ID 使用参数绑定，拒绝由模型提供 SQL。

消息和工具原始内容可能较大：关键事件使用数据库，完整大日志和产物保存在独立内容存储并有引用。避免把每个 token 都单独 FULL 提交；可以批量保存流片段，但要在 UI 标识极端崩溃下的未持久化记录缺口。

### 8.4 文件与数据库的原子性边界

先写临时产物→flush／关闭→计算并验证哈希→同文件系统重命名为固定对象→提交数据库引用。崩溃留下未引用内容可延迟回收，不能先插入“内容已存在”的引用再慢慢写文件。

备份使用驱动在线备份或等价一致性路径；按冻结清单复制引用产物，输出校验清单。普通备份排除秘密。恢复到临时目录执行 `integrity_check`、引用检查和账号缺失提示后，再在停机窗口切换。[S22]

## 9. 调度、排队、等待与竞态

### 9.1 派发选择

每个角色拥有独立新工作队列，FIFO 按入库序号。调度器从所有具备资格的角色中公平选择，不让一个被账号锁住的角色阻塞全空间。

资格条件：角色／空间未暂停；无未处置的独立任务或当前输入为合法续办；原生会话空闲；绑定可用；工作区和命名资源可获得；认证单元允许；预算未触发；无恢复隔离标记。

事务中先记录派发意图和占位，再在事务外调用 Harness。不要持着事务 await。所有事件以 run_id、binding epoch 和原生会话定位符归属，不能根据最近活跃角色猜来源。

### 9.2 当前任务续办

派发子任务时记录 parent_task 和实际 completion 目标。只有确实返回父任务执行角色的结果，才能成为它的续办输入。任务谱系用于预算与追踪，不意味着结果自动抄送祖先。

route_wait 可以声明等待当前任务关联的全部或特定子结果。发送工具不返回成功收据并不妨碍这一功能：Core 根据可信任务关系维护等待集，必要时 route_context 返回业务所需的关联 ID。

等待状态落库与检查已到达结果必须在同一事务逻辑里完成，防止“结果先到、随后进入等待”造成丢失唤醒。结果到达后标记 continuation_ready；直到当前 Run 完全收尾才启动续办。重复结果不重复启动。

### 9.3 防止资源等待死锁

业务等待结束原生轮次后，必须确认没有后台写入再释放执行资源。不要让负责人持有共享主工作区写锁等待另一个需要同一写锁的角色。对已知循环检测生成问题，不自动猜测正确任务顺序。

挂起当前任务应保留任务与上下文，明确释放哪些资源。V1.0 不需要自动抢占任意运行中任务；用户可以取消或在安全边界挂起。审批等待中的原生 Run 仍占会话位置，不得并发注入下一轮。

### 9.4 限流

持久化每次自动启动，包括续办、自动纠错和具有模型调用的重试。按角色短窗口、空间窗口、全局并发和 chain 总量判断。重启保留已发生的启动；单调时钟负责进程内等待，UTC 记录负责跨重启窗口，时钟回拨时采用保守暂停并告警。

限流不阻止保存结果、取消、审批拒绝和诊断。人工“继续”创建有记录的预算授权，不删除旧历史，也不允许模型用新 ID 绕过限制。

## 10. HarnessAdapter 统一契约

下列为拟定 TypeScript 接口，实际定义应由协议包生成或共享。统一的是语义和事件，不是底层全部方法名称。

```ts
interface HarnessAdapter {
  probe(signal: AbortSignal): Promise<CapabilitySnapshot>;
  open(input: OpenSessionInput): Promise<SessionRef>;
  resume(input: ResumeSessionInput): Promise<SessionRef>;
  startRun(input: RunInput): Promise<DispatchReceipt>;
  events(): AsyncIterable<NormalizedEvent>;
  cancel(input: CancelInput): Promise<CancelReceipt>;
  close(input: CloseInput): Promise<void>;
  models(): Promise<ModelOptions[]>;
  history?(input: HistoryQuery): Promise<HistoryPage>;
  account?(): Promise<AccountSnapshot>;
  quota?(): Promise<QuotaSnapshot>;
}
```

`DispatchReceipt` 表示原生请求被接受或提交，不是完成。`CancelReceipt` 表示已发送或收到取消响应，不保证所有副作用已停止。完成仅由 adapter 的 RunSettled 归一化事件产生。

能力快照包含 sessionCreate、sessionResume、history、toolBridge、cancel、approval、modelSelection、reasoningSelection、quota、accountIdentity、readOnlyEnforcement、nativeQueueControl、settledSignal 和认证并发类别。关键能力缺失时拒绝接入；可选能力显示不支持，不能伪造空列表表示全部可用。

事件至少包括 SessionOpened、RunAccepted、TextDelta、MessageCompleted、ToolStarted、ToolUpdated、ToolEnded、ApprovalRequired、RunSettled、RunFailed、Disconnected。原始事件保留必要审计内容并脱敏，规范化事件另有单调序号。历史回放标记 `replay=true`，不能重新执行工具。

每个适配器都要用录制／合成 fixture 验证乱序、重复、断线、截断、超大输出和未知字段。未知新事件可以记录并忽略非关键展示；未知结束或身份语义必须 fail closed。

## 11. Codex 适配器实现

### 11.1 连接与会话

使用 `codex app-server` 的受测 stdio 路径，执行 initialize→initialized，再创建或恢复 thread。从锁定的 CLI 生成类型和 JSON Schema：

```text
codex app-server generate-ts --out <受控生成目录>
codex app-server generate-json-schema --out <受控生成目录>
```

这些输出与生成它们的 Codex 版本对应，禁止长期手写一套猜测字段后宣称兼容所有版本。[S01]

以 `thread/start`、`thread/resume`、`turn/start`、`turn/interrupt` 等受支持方法组成适配器。监听真正结束事件并读取结束状态，不只匹配事件名。`thread/read` 用于历史查看；订阅实时事件是另一条路径，不可互相替代。

每个会话映射 role_id、binding epoch、workspace_id 和原生 thread_id。cwd 绑定满足 V1.0 项目语义；不要求把会话写入原厂桌面侧边栏项目索引。额外原厂项目同步不属于完成接入的先决条件。

### 11.2 内部工具桥与身份

首选受支持的 MCP 配置接入内部 stdio bridge。M00 必须验证会话／进程范围的 MCP 配置、身份归属和权限，不依赖模型自报 thread_id。最保守的方案是每角色独立受控进程和独立桥身份；共用刷新型凭据时通过 AuthUnit 串行化并退出闲置认证写进程。

同一账号的多线程复用可以作为经测试的优化，但需要证明每个工具调用能可靠归属对应线程，且不会共享错误的角色配置。不通过这个验证时不能默认开启。Codex 的 dynamicTools 当前被文档标为实验接口，不作为 V1.0 唯一必需接入路径。[S01]

### 11.3 模型、批准与账号

读取模型及支持推理选项，保存每次 Run 的真实配置。批准请求转为 Core Approval，不在 UI 离线时默认 accept。未实现的反向请求返回明确不支持，而不是悬挂。

账号身份使用管理接口核验；额度只展示该账号与产品可获得的结果，不把 API-key 用量误作 ChatGPT 套餐余额。直接执行绕过线程权限的原生进程控制能力不暴露给角色桥。适配器只允许本版需要且确认权限语义的方法。

### 11.4 必测项

同名角色线程隔离；多个线程事件交错；流末尾没有普通最终文字；工具批准拒绝；退出前写过文件；换 auth 后身份不匹配；恢复旧 thread 但工作区已变化；回放历史不再发信；账号单元串行但其他 Harness 仍可并行。

## 12. Kimi Code 适配器实现

### 12.1 采用当前受测实现，不混用历史目录

目标为用户登记且兼容矩阵通过的 Kimi Code CLI。`kimi acp` 是官方 stdio 接入入口；版本协商后依据真实 capability 启用功能。现行资料包括 `KIMI_CODE_HOME`，但不能把旧实现目录、参数和现行实现随意拼接。[S02][S28]

M00 要核对程序来源、`--version`、`--help` 和初始化响应。版本未认证时可以运行非破坏探测，不能默认启用写任务。版本升级后重新跑契约测试。

### 12.2 ACP 控制路径

实现 initialize、session/new、session/load 或 resume、session/prompt、cancel，以及锁定版本所需的反向 RPC。能力声明要与实际实现一致：文件读取／写入、terminal、权限和询问信息，若声明支持就必须正确响应；没有实现则在握手声明不支持，并确认 Kimi 能在该组合下运行。[S02][S10][S11]

创建 session 时传 cwd 与内部 MCP server 配置，保存 sessionId。模型与推理选项优先读取 configOptions，不把某个别名硬编码成所有账户可选。历史加载可能先回放更新后返回，回放事件仅进入历史投影，不能触发新的业务工具。

ACP 版本不同可能改变 prompt 返回与结束语义。V1.0 仅接受锁定兼容清单中的版本；v1 的结束规则按 v1 规范实现，遇到其他主版本不套用同一 Promise 结束逻辑。[S10][S11]

### 12.3 身份与额度路径

会话执行统一走 ACP，身份与额度可使用官方本地 Server API。两条路径不允许同时对同一原生会话发起执行或修改配置；额度服务不成为第二个会话控制者。

`/api/v1/oauth/usage` 和 `/api/v1/oauth/userinfo` 的包络可能成功而业务数据为 error，需要检查业务 kind。服务启动命令、端口及安全配置从所锁 CLI 的帮助和对应官方版本文档生成启动清单，不猜测旧 `server` 子命令仍存在。[S03]

同一 Profile 的额度查询若会触发凭据刷新，只在认证运行单元安全窗口执行；忙碌时显示缓存与过期时间，不启动竞争写凭据的额外进程。通过并发安全验证后才允许只读共享服务优化。

### 12.4 Profile 切换与历史

每个账号 Profile 有独立受管配置空间。切换不复制整个 home 去冒充另一个账号，也不猜测 OAuth 文件布局。先停止相关执行，再选择目标 Profile，核验身份，恢复受支持的会话定位符。

跨 Profile 原生恢复没有可靠保证时，新建目标会话，加载交接包，保留旧 binding 和本地观测历史，并要求用户确认这一延续方式。状态区别 NATIVE_RESUME 与 HANDOVER_NEW_SESSION，不静默把后者显示成原生无损恢复。

### 12.5 必测项

中文／空格目录，未登录，API-key 与 OAuth 能力差异，加载回放和断开，取消后工具仍收尾，反向权限请求，额度业务错误、区域或身份变化，Profile 切换后旧历史仍可访问。

## 13. pi 适配器与专用扩展

### 13.1 确定目标与入口

pi 特指 pi coding agent。核查时官方仓库 package metadata 的名称为 `@earendil-works/pi-coding-agent`，读取到的版本为 0.85.1；这只是 2026-09-09 的源码观察值，不是已安装或已认证版本，不应直接写成“已测试最新版”。[S26]

V1.0 选 `pi --mode rpc`＋绝对路径加载的 Route 扩展。虽然 pi 提供 SDK 且官方建议 Node 集成者考虑 SDK，本版优先子进程 RPC，以隔离崩溃和依赖并统一进程管理。SDK 可作为后续替换实现，不进入 Core 的领域依赖。[S05][S09]

### 13.2 RPC 不是 MCP，也不是 ACP

pi RPC 使用 LF 分隔 JSON 消息，命令有 type、可选 id，响应与事件异步到达。它不是 JSON-RPC 2.0 的 method/result 模式，不能直接复用 Codex／ACP 的反序列化逻辑。官方文档特别要求 LF 分帧；使用自行实现的 UTF-8 增量缓冲，按 LF 分割、允许尾部 CR、限制最大帧，不使用会把其他 Unicode 分隔符当边界的通用行读取器。[S05]

维护请求关联表、部分 UTF-8、半帧、stdout 背压、未知事件记录和 stderr 分离。扩展不能向 stdout 打普通日志，否则会破坏协议。二进制错误输出不能当作合法 JSON 忽略后继续宣称连接正常。

### 13.3 关键命令与结束信号

使用受测的 prompt、get_state、get_messages、get_available_models、get_available_thinking_levels、set_model、set_thinking_level、abort 等命令。创建／恢复使用明确 session 目录和定位符，不在受管角色上使用 `--no-session`。

prompt 响应表示接受、排队或处理，不代表运行结束。当前官方文档区分 agent_end 和 agent_settled：前者后面仍可能出现自动重试、压缩重试或排队续办，后者表示整个 session-level run 真正安定下来。适配器必须用锁定版本的最终收尾语义归一化 RunSettled，不以 turn_end、message_end 或 agent_end 直接放行下一任务。[S05]

旧版本没有可靠 settled 信号时，不靠固定 sleep 代替证明。应选择符合能力要求的受测版本；若确需兼容，必须有完整状态／队列／重试核对状态机和专门 fixture，不作为默认回退。

### 13.4 工具扩展

pi 不原生提供 MCP；它支持扩展注册工具。编写自有 `agentrouter-tools.ts`，注册与其他 Harness 一致的 Route 工具，将调用发往同一个 Core。无需为了 V1.0 再安装一个未审查的第三方 MCP 包。[S04][S06]

受控扩展根据进程初始化身份取得 binding token；toolCallId 可参与幂等操作关联。工具参数仍按总协议校验。普通发送成功返回最小技术结果；context、artifact 工具返回实际所需数据。

当前扩展 API 有 `terminate` 结果提示，可用于 finish／wait 减少无意义后续生成，但它只在满足工具批次条件时生效，不能代替 RunSettled 检查。[S06]

### 13.5 禁用第二套调度与隐式代码加载

Route 是唯一任务队列。V1.0 不使用 pi steering／followUp 作为第二个业务队列，不加载会自动生成 sub-agent 的第三方扩展，不让 pi 内部后台链绕过 Route 的预算记录。

通过经核查参数禁用扩展自动发现，并显式加载唯一受控扩展。默认不信任项目本地可执行资源；项目 AGENTS 等文本指引可以按策略保留。`--no-approve` 一类选项针对项目信任，不等于阻断所有危险命令。pi 的强权限需求必须额外验证，不能声称原生就有与 Codex 相同的沙箱。[S04][S06]

### 13.6 对话、用户交互和 Windows

通过 message／tool 生命周期构建对话，get_messages 补足可得历史。扩展 UI 的 confirm／input 请求转为用户批准或输入事件，超时按保守拒绝／取消处理。展示型 notify 不自动生成业务回复。[S05]

Windows 默认 Bash 路径需探测。可选 PowerShell 工具是能力，不应未经用户同意替换 Shell 或改变命令语义。实际命令、编码和退出码都进入兼容测试。[S08]

## 14. 工具桥、身份与幂等的实施细节

### 14.1 Principal

内部调用上下文至少包含 principal_type、project_id、space_id、role_id、binding_id、epoch、允许工具范围。当前 task_id 和 run_id 由 Core 的受控运行槽确定，不从模型 payload 接受。原生一条连接对应多个会话时，必须有不可伪造的会话关联机制；没有则按角色拆开进程。

长寿命 bridge 的 token 只代表绑定，不代表永远可执行任意任务。每次副作用调用还要核对当前 Run、代次和状态；结束或替换后旧工具调用被拒绝或转入迟到事件，不继续修改任务状态。

### 14.2 幂等操作身份

优先以已验证的原生 toolCallId＋binding＋Run 构造稳定关联；没有稳定原生 ID 时，bridge 在首次发送前生成 operation_id，并为同一次受控传输保留映射。进程重启无法确定原调用身份时，不用新 ID 盲目重发。

Core 的 operation ledger 记录 canonical request hash 和处理结果。已有操作重复时返回同一最小技术结果；不同内容同 ID 拒绝。链路超时但可能已落库时，先按同 ID 查询／重试，不能告诉模型“肯定没发送”。对无可靠原生重放标识的工具调用，人工或原生历史核对是受支持退路。

### 14.3 配置的最小暴露

内部 bridge 无 create_role、switch_account、install_plugin 或 arbitrary_api_call。敏感环境变量采取白名单构造，不复制整个主进程环境。路径和模型参数通过参数数组传递，禁止拼接到可注入 Shell 字符串。

模型输入可能影响产物路径或任务文本，不能影响可执行文件路径、认证文件路径或本地管理端点。工具名称、Schema 与实际注册版本有快照，避免会话缓存旧工具定义后发生静默行为变化。

## 15. 工作区、文件引用与规则发布

### 15.1 物理目录识别

区分 display_path 与 canonical_path。Windows 要处理大小写、盘符、UNC、junction／reparse point、空格、中文和长路径。应用数据库只支持本地数据目录；源工作区的网络路径在 V1.0 默认未认证，不把它与本地 NTFS 混为一谈。

所有内部相对路径拒绝 `..` 越界、绝对路径注入、设备名与 ADS 等不受支持形式。解析后再核对允许根目录。路径校验减少误用，但对拥有写入权限的敌对进程存在 TOCTOU 风险，不得据此宣传 OS 沙箱。

### 15.2 worktree 管理

从用户明确选定的仓库和提交创建；使用参数化进程调用，不执行拼接命令。记录 repository_id、base_oid、branch、workspace_id 和状态。创建／删除前检查未提交变化、其他活跃 Run 和产物引用。永远不默认 `reset --hard`、`clean -fd` 或强制移除用户工作树。

资源锁至少支持 workspace.write、integration.write 和用户命名资源。主目录写任务默认互斥，读任务对稳定版本的要求由任务输入确定。不能让共享 Git 元数据变更与另一个删除／迁移 worktree 操作无保护并行。[S20]

### 15.3 产物与 Git 引用

Git 固定引用保存完整对象 ID，按仓库对象格式校验，不只接受 40 字符从而错误拒绝其他受支持格式。解析路径时固定提交；必要时创建受管保留引用或将正式交付内容复制入产物存储，避免垃圾回收导致历史不可读。[S21]

未提交报告和补丁冻结为内容对象，数据库保存媒体类型、大小、哈希、来源和保留状态。live 引用显式可变；external 引用仅登记，未经授权不自动联网解析，防止任意 URL 成为 SSRF 或带凭据访问入口。

### 15.4 规则发布与镜像

Core 保存不可变 PolicyRevision。用户批准后生成 workspace 镜像，AGENTS.md 只增加带标记的受控区块并保留旧内容。自动生成目录是否加入本地排除规则需展示变更并经用户同意，不悄悄修改全局 Git 配置。

任务固定 revision。角色上下文每次工作提供身份、协议版本和规则引用，恢复／新绑定时提供必要摘要。项目文件改动不直接改变已发布权威规则。发布者身份是用户或已授权服务，不因某角色名为 Control 自动获得发布权。

## 16. 账号、认证运行单元和额度

### 16.1 AccountProfile 与 AuthUnit 不同

AccountProfile 表示身份档案和秘密引用；AuthUnit 表示可能共享凭据刷新、配置或登录状态的运行资源。调度器依据 AuthUnit 限制并发，不能因为创建了不同文件夹就证明同一 refresh token 可以安全并行。

V1.0 保守基线允许不同 Harness／独立认证运行单元并行；同一刷新型凭据未经验证时串行。多角色共享一个原生服务的高级并发必须通过工具身份、刷新和会话隔离测试后才启用。这个限制要在 UI 显示，并不等于整个项目串行。

### 16.2 Codex 文件切换事务

Codex 采用专用受管 runtime home，显式文件后端。账号档案与原生活跃 auth 分离；原生读取所需的明文文件只存在受限运行目录，不进仓库和一般备份。[S14]

切换状态：REQUESTED→PAUSING→QUIESCING→SNAPSHOT_OLD→INSTALL_TARGET→VERIFYING→COMMITTED；任何失败进入 FAILED_SAFE 或 ROLLBACK_REQUIRED，并保持相关派发暂停。

先记录切换意图，列出受影响 PID／角色，由用户批准关闭或等待；检查所有相关受控进程和额度查询已停止；保存旧账号最新刷新文件；在同文件系统安全写目标临时文件，检查格式和限制权限，再替换；启动后调用身份接口核验；成功才恢复。

文件系统更换与数据库不是一个原子事务，使用切换日志和恢复步骤。任一断点重启后不猜当前身份；先核验，必要时回滚。管理员策略要求 keyring 时拒绝文件切换，而不是尝试绕过。刷新后的凭据不能每次被原始种子覆盖。[S14][S15]

### 16.3 Kimi 与 pi

Kimi 使用 Profile 目录绑定与官方身份路径，不照搬 Codex auth 字段。跨 Profile 的会话恢复属于条件能力；必要时转显式交接新会话。V1.0 不实现凭据文件内部格式的逆向拼接。

pi 使用受控配置目录和已配置提供商。可通过官方环境／配置方式指定认证，但不把密钥作为命令行参数。API-key 与刷新型 OAuth 的并发策略不同；与其他 Harness 共享同一账户资源时仍记录可能的共享预算，不假定各自有完整独立余额。[S07]

### 16.4 额度快照

统一结构包括 harness、provider、account_ref、product、region、window、used、limit、remaining、reset_at、observed_at、source、status。字段不适用就留空并说明，不进行无依据换算。费用和 token 统计单列，不能当额度余额。

手动刷新加保守缓存，轮询受速率限制。忙时优先使用缓存，不为查询切换账号。认证失效、套餐不支持、业务 error、网络错误和 stale 分开显示。配额查询不阻塞数据库核心或被当作自动跨提供商路由依据。

## 17. Windows 进程管理、托盘和退出

### 17.1 受控进程树

仅调用 child.kill 不足以证明孙进程停止。发布版应使用小型 Windows supervisor，通过 CreateProcessW 的受控启动、Job Object 归属及进程句柄管理建立受管进程树。关键属性包括 Kill-on-job-close、禁止未授权 breakaway，并验证父进程已处于 Job 时的兼容性。[S25]

辅助程序只承担启动、stdin/stdout/stderr 转发、句柄和终止；不理解业务协议，不记录秘密。优先在启动目标执行代码前完成 Job 归属，避免先运行再纳管的竞态。构建依赖 Windows SDK，但发布包不应要求用户安装编译器。

使用 PID 之外的创建时间／句柄核对归属，防止 PID 重用误杀。taskkill 可作为开发诊断，不能把 `taskkill /IM codex.exe` 作为正式停止方案。无法证明退出的工作区保持隔离，交给用户处理。

### 17.2 正常取消

先发原生取消，等待受测最终状态，必要时进入受控进程终止。超时是升级处理条件，不是“任务肯定没做”的证据。取消时已经冻结的结果和实际修改保留核对，后续消息不会自动沿成功路径释放。

### 17.3 窗口与 Core 生命周期

关闭窗口时不关闭 Core 的 stdio 或内部工具端点；主进程保留托盘，Core 和 Harness 继续。重新打开 UI 订阅事件并读取当前状态，不重复 startRun。[S18]

“当前轮次结束后暂停”先写 pause intent，再等待活跃 RunSettled，不继续后续自动接力。若有审批等待，用户可保留后台等待或选择取消，不能把无人响应当批准。

真正退出、主控丢失或系统退出时，持续保存的状态是恢复依据，退出钩子只是尽力收尾。V1.0 不承诺主进程完全崩溃后继续无人监管协作；Core 检测宿主失联后停止新派发，按可行策略取消／隔离已有运行。

## 18. UI、事件投影与人工操作

### 18.1 必需页面

项目列表与主页；协作空间；角色创建／设置；角色对话页；协作时间线；新工作队列；用户收件箱；问题和审批中心；账号与额度页；工作区与产物页；备份／诊断／兼容设置。

UI 中必须同时展示任务意图、原生运行状态和交付状态。来源身份来自 Core，不由 summary 内自报名字决定。busy、paused、rate_limited、auth_locked、workspace_locked、reconciling 等等待原因应可解释。

### 18.2 事件流

UI 使用 Core 单调事件序号；重连先取得一致投影和 cursor，再订阅之后的事件。防止 snapshot 与 subscribe 之间丢事件，可由服务提供 snapshot_at_seq，并回放此序号之后事件。

前端可以显示待提交动画，但不能提前将任务标成已保存／已完成。大对话虚拟列表、日志分页、增量合并和输出背压是必要性能措施。模型 Markdown 禁止原始 HTML 执行、任意脚本和不受控外部资源加载。[S19]

### 18.3 人工输入

空闲角色可接收管理对话；忙时默认排队。加入当前任务需选择明确任务并记录关联。中断是独立控制动作，不把所谓高优先级消息直接注入原生输入流。确认／驳回结果要保存操作者与具体产物版本，已读状态不算验收。

## 19. 故障分类、重试与恢复流程

| 故障位置 | 可自动做什么 | 禁止做什么 |
|---|---|---|
| 验证前 | 返回可修正错误 | 返回成功 |
| 已保存、未派发 | 重建队列 | 丢弃任务 |
| 派发写入确认未知 | 查询原生会话和事件、隔离资源 | 换新 ID 盲目重发 |
| Run 已修改文件但结果缺失 | 收集证据并请求核对 | 以无回复判断未执行 |
| 结果已保存、未收尾 | 保留 HELD 消息和产物 | 自动启动下一阶段 |
| UI 崩溃 | 重新订阅 Core | 再启动同一任务 |
| Core 崩溃 | 重启进入恢复模式 | 自动释放所有旧写锁 |
| 账号切换中断 | 读取切换日志并验证身份 | 根据文件名恢复派发 |

恢复启动先取得单实例锁，检查 SQLite／迁移，标记未完成 Run 为待核对，核实原 PID 和认证状态，恢复持久队列，再逐项解除隔离。不能直接把所有 RUNNING 改 QUEUED。

自动重试仅适用于已证明未执行的调用，或操作本身具有可靠幂等性。退避与次数限额单独记录；一个 transport request ID 不自动提供跨重启幂等保障。对误操作的撤销由项目工具能力决定，不由 Router 泛化承诺。

## 20. 安全、秘密与扩展边界

### 20.1 系统控制与业务授权

角色工具只允许受限项目范围。Bridge token、数据库、账号目录不在工作区内。对于文件／网络的实际限制，使用原生能力和平台约束；不支持的强约束直接拒绝配置，或由用户显式选择受信运行模式。

pi 受控扩展可以做工具确认或保护路径，但不是恶意代码沙箱。扩展加载、包安装和提供商变更必须由用户操作；项目规则不能通过字段隐式安装代码。[S06]

### 20.2 秘密与日志

秘密只存受限用户目录或受平台保护的秘密存储，Core 数据库存引用和脱敏身份。适配器读取认证文件的操作不得写入聊天历史。禁用调试级完整环境转储；错误消息剔除 Authorization、token、cookie 和原生认证文件内容。

脱敏是尽力防护，不保证任意源码或路径无敏感信息；诊断导出前给用户预览文件清单。备份的秘密是否包含需独立授权和加密设计，V1.0 默认不包含。

### 20.3 外部 MCP 与 API 预留

Core 应用服务接受 Principal、scope、operation_id、protocol_version、cancellation 和 event cursor。未来外部插件只作为新调用者复用同一服务，不直接写 SQLite。

V1.0 不开放外部管理监听端口、不注册远程编排工具、不实现任意 URL API 代理。外部 IntegrationAdapter 未来需要声明输入输出、凭据引用、副作用、幂等和批准策略；现在只保留接口与假实现测试。

## 21. 可行性与稳定性逐项评估

| 能力 | 可行性判断 | 主要风险 | V1.0 处理与发布条件 |
|---|---|---|---|
| 角色与项目管理 | 高 | ID／路径混淆 | 唯一身份、路径规范化、归档非删除 |
| 可靠消息 | 高 | 重试重复、未知窗口 | ledger＋outbox＋恢复隔离 |
| 三家会话调用 | 有官方入口 | 版本语义变化 | 精确版本、契约 fixture、真实端到端 |
| 统一对话页 | 可实现协议可见部分 | 历史缺口、错误回放 | 本地事件存储、replay 标识 |
| 并行工作 | 可实现 | 文件、端口、账号冲突 | 独立工作区与资源限制 |
| 文件版本交接 | 高 | 仅有索引却无内容 | 冻结对象、Git 保留、校验 |
| Codex 换账号 | 有依据、需实测 | 刷新竞争、错账号、中断 | 停止、保存最新凭据、切换日志、核验 |
| Kimi Profile 切换 | 可实现账号选择 | 跨 Profile 原生历史不兼容 | 原生恢复或明确新会话交接 |
| pi 工具桥 | 可实现 | 扩展执行代码、事件结束判断 | 自有扩展、固定版本、agent_settled |
| 窗口关闭继续 | 高 | 误关控制连接 | 托盘保留 Core，重连不重启任务 |
| 崩溃自动恢复 | 部分可自动 | 外部副作用不可证明 | 可恢复与人工核对分开 |
| 强安全隔离 | 非默认保证 | 同用户完整系统权限 | 暴露能力边界，拒绝伪装沙箱 |

这些是工程分析，不是故障率统计。优先选择能解释失败并停止的方案，而不是看似自动但无法确认副作用的方案。

## 22. 自动化测试分层

Domain 单测覆盖每个状态转移、非法转移和权限矩阵；Storage 测试覆盖真实驱动事务、唯一性、迁移和备份；Scheduler 测试使用可控时钟、模拟并发与故障；Adapter 契约用录制样本和合成流；Desktop 测试验证真正打包后的路径、秘密、托盘和退出；Live Harness 测试验证三家实际账号与会话能力。

CI 默认离线运行模拟测试，不使用真实账号。真实测试需用户提供已授权环境，并将秘密与输出脱敏；缺凭据时标 BLOCKED_ENV，而不是伪造通过。可以继续完成其他不依赖该环境的模块，但发布 Gate 不计为通过。

关键故障注入点：数据库提交前后、写入 outbox 前后、发送首字节后、收到原生接受前后、产物写完未引用、finish 后未收尾、切换认证的每一步、进程终止超时、系统时间回拨、UI 重连。

最少还要覆盖：重复工具事件、消息反序、超大帧、UTF-8 半字符、U+2028／U+2029、CRLF、stderr 污染、无最终自然语言、pi 自动重试、Kimi 回放、Codex thread 交错、模型配置不支持、普通通知不唤醒。

## 23. 开发顺序与里程碑 Gate

### M00：需求冻结、兼容探测与打包骨架

读取本包，建立功能清单与 ADR。完成私有 Node／Electron／SQLite 加载、模拟子进程、桥入口和 Windows 安装路径的最小打包样本；用只读探测核对三家版本、入口、模型与工具能力。产出 compatibility-lock、原生协议样本和差异清单。

Gate：打包后的程序在无开发工具依赖的目标机上可加载数据库和模拟 Harness；确证三家有受支持的会话与工具桥路径；无法确认的项明确 BLOCKED，不凭猜测冻结。

### M01：协议、领域和数据库

实现 Schema、错误码、身份、Task／Run／Message 分层、迁移和仓储。编写请求、完成、通知、索引、规则样例及反例。实现不变量单测和跨表事务测试。

Gate：有效样例全部通过；无效目标、伪造身份、同 ID 不同内容、半事务和非法状态全部被拒绝；数据重启可读。

### M02：模拟 Harness、工具桥、调度与恢复

实现 role bridge、operation ledger、队列、续办、outbox、finish 屏障、限流和恢复模式。模拟 Harness 可脚本化发事件、调用工具、制造崩溃和副作用。

Gate：没有真实模型也能完整跑 A→B→C→用户及并行汇总；静默成功、指定结果、不重复唤醒和故障隔离有测试证据。

### M03：Codex 纵向闭环

接入真实 Codex，提供最小角色对话页、输入与结果列表，验证工具注册、原生结束、批准、取消、历史和断连。先完成一个角色，再完成两个角色和队列；共享认证默认受限。

Gate：真实消息与产物可追踪；取消不虚报；恢复不重放旧业务工具；UI 不靠终端文本猜状态。

### M04：Kimi Code 与跨 Harness

完成 ACP、反向请求、会话加载、模型配置和工具桥，加入用户收件箱。验证 Codex 发给 Kimi、Kimi 返结果、指定第三角色或用户，不隐式抄送。

Gate：原生历史回放无副作用；两家任务身份无混线；能力不支持时有明确状态。身份／额度基础接口可以在本阶段加入，但完整切换流程在 M08 通过。

### M05：pi RPC 与受控扩展

实现 LF 分帧、事件归一化、工具扩展、模型和 history、abort、extension UI。禁用原生二级队列和未审查扩展，验证 agent_end 后重试与 agent_settled 的区别。

Gate：pi 不需要假定原生 MCP；三家协议同样通过 Route 契约；pi 正式支持必须通过与另外两家相同的功能验收，不以“实验”标签代替本版要求。

### M06：并行工作区、版本产物与规则

加入目录规范化、Git worktree、工作区和命名资源、固定产物、Git 保留引用、项目规则发布和更换 Harness 的交接包。补全角色管理、停用与历史绑定。

Gate：两个独立角色真实并行；同物理目录跨空间仍互斥；已提交产物后原文件改变不会污染复核；恢复旧会话前补齐项目进展。

### M07：完整桌面体验、后台与 Windows 停止

完成角色页、时间线、队列、问题中心、权限界面、托盘和窗口恢复。正式纳入 Windows Job supervisor，覆盖子进程与孙进程，补全日志背压和输出分页。

Gate：关窗口不中断选择保留的工作，重开不重复；当前轮次后暂停不启动接力；审批不默认批准；停止不误杀用户独立进程。

### M08：账号、额度、备份和诊断

完成 Codex auth 切换日志和身份核验，Kimi Profile 切换与原生／交接提示，pi 提供商展示，额度窗口缓存；实现一致性备份、恢复、脱敏诊断、迁移回滚计划。

Gate：所有切换断点可恢复为安全暂停，旧凭据刷新被保留；未知额度不当无限；跨 Profile 无法恢复时不虚报；备份在临时目录完整恢复。

### M09：发布验收与缺口关闭

跑完整追踪矩阵、真实 Windows E2E、长时间压力与故障注入，固定依赖和可执行文件清单，验证安装／卸载不删除用户项目，更新功能手册实际能力和已知限制。

Gate：F01—F25 的适用用例通过，F26 仅预留接口且未意外开放；三家适配必需能力真实通过；无未解释的数据丢失、重复副作用、错身份投递或遗留写入。未通过就不能把对应能力标为 V1.0 已交付。

## 24. 每次提交给 Codex 的任务格式

每项开发任务应说明目标功能编号、修改范围、依赖里程碑、要新增的测试、禁止改变的语义、证据路径和完成条件。允许 Codex在职责内选择内部实现细节，但不得擅自增减产品范围。

实现顺序为先写失败测试或契约样例，再写最小实现，运行相关测试，检查日志和安全影响，最后记录完成状态。每次阶段报告区分 implemented、tested、blocked、known_risk；测试命令必须附退出状态，不写未运行的“全部通过”。

不要以创建大量空目录、TODO 或固定假数据代替功能。模拟适配器保留明确 mock 标签，不得出现在真实 Harness 支持计数中。对原厂接口差异，记录证据和 ADR 后修正适配器，不修改协议来迎合未经验证的终端输出。

## 25. 建议命令与持续集成契约

仓库建立后应提供稳定命令：`pnpm lint`、`pnpm typecheck`、`pnpm test:unit`、`pnpm test:integration`、`pnpm test:contract`、`pnpm test:chaos`、`pnpm test:desktop`、`pnpm build:win`、`pnpm test:packaged`。这些是实施要求，不是本文件包已经能执行的应用命令。

提供 `doctor` 输出脱敏环境和兼容状态；`spec:check` 验证 Schema、示例和跨文档枚举；`db:verify` 验证实际 SQLite 版本、外键、integrity 和迁移；真实联调使用单独授权脚本，不在公开 CI 自动使用用户凭据。

维护 REPRODUCTION.md，使另一开发者能从安装包和固定测试 fixture 复现关键失败。Windows 主机测试是发布必需，不以 Linux 上单测通过替代。

## 26. 备选方案与不采用的原因

| 备选 | 为什么不作为 V1.0 默认 | 何时重新评估 |
|---|---|---|
| 所有工作强制串行 | 削弱用户的核心并行需求 | 单个受限工作区或认证资源仍可串行 |
| 全部强制 ACP | pi 原生不是 ACP，多一层桥增加差异 | 未来有稳定官方统一入口 |
| pi SDK 嵌入 Core | 依赖与崩溃边界更紧 | 独立 worker SDK 通过更好测试或性能证明 |
| 解析终端／桌面自动化 | 状态和工具身份难稳定验证 | 仅故障诊断，不作正式接入 |
| 任意自动重试 | 可能重复文件或外部操作 | 外部端点具备可靠幂等证据 |
| Temporal／多机队列 | 增加部署与运维，不自动解决副作用 | 多机、高可用成为真实需求 |
| 全面角色权限矩阵 | 与业务自由编排目标不匹配 | 多用户或强隔离需求出现 |
| 隐式共享所有原生账号目录 | 刷新、会话和配置竞争 | 经验证的共享运行模型 |
| 自由加载第三方 pi 扩展 | 任意代码与隐藏调度难纳管 | 可信插件体系和权限契约完成 |

## 27. 发布物与维护要求

发布物应包含 Windows 安装包或受测便携包、私有运行时与必需 helper、协议与模板、版本清单、第三方许可、升级与恢复说明、功能手册和已知限制。原厂 Harness 默认由用户已有安装或明确同意的安装流程提供，不暗中下载和执行未经校验代码。

应用升级先暂停新派发和做一致性备份，不在活跃写任务中更换协议或数据库。协议主版本变化需要显式迁移；未知消息版本拒绝执行，保留可诊断信息。不可逆数据库变更必须提供恢复旧备份路径，而不是假定降级可直接读新格式。

## 28. 最终实施原则

V1.0 的价值来自可观察、可交接、可恢复的协作，不来自角色数或框架数量。业务决定由人和指定 AI 作出；Core 负责准确执行并说明状态。保留人的控制权，不用自动化掩盖不确定性。

发布前优先证明：成功静默但不丢消息；结果只到指定对象；新任务排队但当前结果能续办；三家原生结束语义正确；并行不共享错误身份；版本不会漂移；账号切换不边运行边覆盖；关闭窗口不破坏控制连接；恢复不盲目重跑。

官方事实、接口名称和限制统一引用 `07_研究依据与版本核查.md`。本手册的状态机、队列、数据模型、UI 和里程碑是针对 AgentRouter 的设计建议，不是官方 Harness 的自带功能。
